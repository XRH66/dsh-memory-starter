- **V2＋重排低分救援 0.50**：语义预取 `91/95`，比 V0 多 23 题；事实覆盖 `40/40`；字面 `40/40`；有答案错注入为 3 题。代价是无答案误注入升到 `34/40` 题、`70` 条，且所有有答案题合计实际注入 303 条材料，V0 为 120 条。

- **V1 候选扩到 30**：主动搜索提升明显，预取只多 3 题；最终 token 比 V0 多 104,892。和 V2 组合后没有超过单独 V2，反而把 token 推到 223,565。

证据支持的优先候选是 **V2**，它在命中、主动搜索和成本之间最平衡。若目标是尽量不漏，**V2＋0.50 重排救援**能把事实覆盖补到 `40/40`，但需要用户明确接受大量无答案误注入；不建议直接把该救援规则定为默认。

## 2. 执行边界

测量复用 DC 的真实插件路径：

- 原话写入 `RawMemoryStore`，在系统临时目录建立独立 SQLite。
- 原话全文检索走 `createRawRecall().queryReader()`。
- 向量索引走 `createMemoryVectors()`。
- 重排走 `createMemoryReranker()`。
- 自动预取和主动搜索都走 `createMemoryQueryAnswer()`。
- 自动预取的最终准入仍调用各变体自己的 `selectPrefetch()`。

测量只允许请求 `https://api.siliconflow.cn/v1/embeddings` 和 `https://api.siliconflow.cn/v1/rerank`，并逐请求校验模型名必须是：

- `BAAI/bge-m3`
- `BAAI/bge-reranker-v2-m3`

密钥只由插件在请求时从 `BENCH_EMBED_KEY_FILE`、`BENCH_RERANK_KEY_FILE` 指向的文件读取。测量脚本只检查文件可访问，没有读取、显示或记录密钥内容。非密钥检索参数按 DC 回执固定；没有读取日常部署目录或 `.local/runtime/` 下的文件。

## 7. 各变体利弊

### V0 现状

- 复现 DC：语料一语义预取 `33/43`、主动搜索 `36/43`、字面预取 `18/18`。
- 漏项主要是候选完全未召回、重排绝对地板拦住强向量候选。

### V1：向量通道 10 → 30

- 合计语义预取只多 3 题，但主动搜索多 9 题。
- 预取重排 token 中位数从 `304/401` 升到 `451/573.5`，总 token 增加 104,892。
- 放宽向量通道能把目标带到更后面，但不能稳定穿过预取只重排前 16 条的限制。

### V2：只编码正文

- 两个语料都有效：C1 从 `33/43` 到 `39/43`，C2 从 `35/52` 到 `37/52`。
- 主动搜索升到 `94/95`，事实覆盖 `39/40`。
- 错注入没有变差：有答案题从 4 降到 2，无答案题只多 1 题、1 条。
- 因为索引材料不再重复背景，最终有效结果 token 比 V0 少 21,576。
- 剩余漏项已经高度集中在重排地板：C1 4 条全部是地板；C2 15 条中 14 条是地板、1 条候选未召回。
- 风险是本批没有专门测依赖前文指代的问法。去掉背景可能在“刚才那个”“上次说的那家”等真实对话里损失上下文，本批两组语料不能证明无影响。

### V3：带背景、只正文双向量

- 命中、主动搜索、错注入和 V2 基本相同。
- C1 索引分块 `150 → 300`，C2 `132 → 264`。
- 相比 V2，全部结果 embedding token 增加 22,794，总 token 增加 23,314。
- 它的潜在优点是保留带背景向量，对真实对话中的前文依赖更保守；但本批没有测出召回收益。

### V4-045 / V4-050：低重分强向量候选救援

- V4 只改自动预取，所以主动搜索完全不变。
- 0.45 档 C1 语义从 33 到 36，C2 从 35 到 44；但无答案误注入从 V0 的 15/40、16 条升到 37/40、87 条。
- 0.50 档 C1 为 35，C2 为 40；无答案误注入仍有 29/40、51 条。
- 该规则会把相似但不需要的历史材料带进无关问题。不能只看有答案命中提升。

### V5：最多 3 → 4 条

- 两份语料全部指标与 V0 相同。
- 说明在当前重排配置下，第 4 条截断不是主要瓶颈。该单项没有现实收益证据。

### V1＋V2

- 与单独 V2 完全相同的预取、搜索、事实覆盖和错注入。
- 总 token 从 V2 的 120,592 增到 223,565，没有换到命中收益。

### V2＋V4-050

- 合计语义预取从 V0 的 68 升到 91，C1 达到 `43/43`，C2 达到 `48/52`；事实覆盖 `40/40`。

### V1＋V2＋V4-050

- 总 token 多 102,956，没有换到额外命中。

## 9. 推荐和需要用户决定的取舍

### 推荐

按本批证据，**V2 是默认候选的优先方案**：

- 不增加接口请求数或候选数。
- 两份语料合计语义预取多 8 题，主动搜索多 12 题，事实覆盖多 4 条。
- 字面问法没有回退，无答案误注入只多 1 题、1 条。
- 最终有效结果 token 比 V0 低。

但 V2 的“去背景”会影响真实对话中对前文指代的检索，本批没有覆盖这类问法。因此它是当前数据的优先候选，不是无需用户确认的最终方案。

### 需要用户决定

1. **召回与误注入怎么取舍**
   - 选 V2：`76/95` 语义预取、`39/40` 事实覆盖，无答案误注入 `16/40`、17 条。
   - 选 V2＋0.50 救援：`91/95` 语义预取、`40/40` 事实覆盖，但无答案误注入 `34/40`、70 条。
   - 两者差异不是小修：高召回方案会让约 85% 的无答案问题带入材料。

2. **是否保留背景向量**
   - V2 成本最低，但对依赖前文的真实问法有未测风险。
   - V3 同时保留背景和正文，当前两组语料同 V2 命中，索引分块翻倍。是否为了未知的真实场景买这份保险，需要用户定。

3. **候选通道 30 是否值得**
   - V1 对主动搜索有价值，但预取收益小，token 成本高。
   - V1＋V2 和 V1＋V2＋V4 都没有超过各自不带 V1 的组合，本批没有理由把这些组合放前面。

4. **最大 4 条的优先级**
   - V5 没有收益。当前证据不支持把它作为本轮主修法。
