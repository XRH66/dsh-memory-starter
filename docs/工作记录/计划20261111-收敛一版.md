## 第 2 步调查记录（2026-11-11）

- 不检索就答、只调一次模型的题，输入明显分成两档：约 7.6k 和约 20.2k，相差约 12.5k；和记忆库大小无关。
- 每题都会注入：回答规则、跨会话交接（默认预算 4096 估算词元）、按用户原话预取的最多 4 条相关记忆（有字数上限）。这三样加起来解释不了多出的 12.5k。
- 高档和间隔天数相关：当天的题 35% 在高档，45 天后的只有 7%。
- 高档并不等于浪费：当天的题，高档通过率 84%，低档 66%。多出的内容很可能是对近期题有用的上下文。
- 结论：静态读代码确认不了这 12.5k 是什么。要么开请求记录跑一次小冒烟实测，要么这一版不动它。在弄清之前不按猜测删减。
- 用户决定：这一版先不动，第 3 步取消，留到下一版查清楚再说。

## 复测中发现的问题（2026-11-11，用户已同意加入这一版，即第 3b 步）

在隔离副本上用硅基流动重建索引复测时，连续两次中途失败：一次 HTTP 400，一次 503「Model service overloaded」。请求是一个接一个发的，间隔中位约 156 毫秒，和修复前相同，不是发得太快。

查下去发现：`lib/raw-rag/cloud-backend.js` 的在线向量适配器只要失败一次就把自己设为暂停（`blocked`），之后所有向量请求直接失败。本地模型会在空闲后释放、重建、恢复，但 `lib/raw-rag/backend.js` 的 `scheduleIdleRelease` 明确排除了在线模型（`engine==='api'`），所以**在线向量一旦失败，要到重启 DSH 才恢复**。期间检索只剩文字通道，用户看不出来。后台队列虽然有 3 次重试，但暂停后每次都立刻失败，等于没有。

建议修法：只在结果不确定（超时、连接中断）时暂停；服务明确回了错误状态（过载、限流、请求无效）就不暂停；暂停几分钟后自动放行一次。

## 不在这一版

- 去掉 Basic Memory、改名、删除旧召回链（E11）；
- 「只核对改动的那几条」、建索引时合批请求（计时器修好后日常收益只剩几秒）；
- 整理策略的大调整（何时整理、整理多少），以及其他针对费用的结构性改动。
