## 实现

### 原路径与 rc.5 能力

- `lib/normal-driver.mjs` 原先通过 `ctx.sessionController.create({ sessionId, workspace })` 开题。
- rc.5 的 `ApiSessionAgentController.createAgent()` 实际执行 `(await ctx.agents.create(...)).agent`，句柄被丢弃。
- `ctx.agents.get()` 只返回裸 `Agent`，不返回带 `dispose()` 的句柄；Session Controller 也没有 `close`、`release` 或按 id `dispose` 的公开方法。
- rc.5 的正式生命周期接口是 `AgentHandle.dispose()`。其文档明确说明它会停止循环、注销代理、移除会话并释放作用域。

### 新题会话创建

`createExam()` 现在直接调用公开的 `ctx.agents.create()`：

- 保留返回的 `AgentHandle`。
- 通过公开的 `agentPresets.resolve()` / `mount()` 复现 Session Controller 的默认预设装配。
- 显式传入题目模型和 `cwd`。
- 创建后仍调用 `ctx.sessionController.selectModel()`，再开启记忆、设置只读并核对状态。
- 如果创建后的初始化失败，立即尝试释放刚创建的句柄。

### 落盘后释放

每题成功路径的顺序是：

1. 收集本题前后的预取和检索摘要。
2. 追加 `exams.jsonl` 与 `answers.jsonl`。
3. 更新 `progress.json`。
4. 以原子替换写入 `searches.jsonl`。
5. 在 `finally` 中调用 `handle.dispose()`。

`searches.jsonl` 不再只等整轮结束才写，而是每题结束时合并并落盘；快照答题模式仍会保留此前进程已有的检索行。释放结果写入：

`<运行目录>/<人物>/session-releases.jsonl`

记录包含题号、会话号、尝试次数、答案与检索是否已落盘、释放前后的活代理数、释放耗时、代理是否仍存活、会话是否仍挂载和错误信息。释放函数整体兜底，释放或核对异常不会覆盖原来的题目错误，也不会中断后续题。

### 对照开关

设 `BENCH_KEEP_EXAM_SESSIONS=1` 时跳过 `dispose()`，只写一条 `skipped=true` 的释放日志，代理数保持不变。该开关只影响考试会话；历史回放会话不释放。

## 发现

1. **需要 Claude 决定：快照热身会话仍不释放。** `warmupSearch()` 每个快照答题进程创建一个热身只读会话，任务只要求释放考试会话且明确历史回放不改，因此本批没有扩大处理。如果以后快照模式也按 cutoff 连续启动多个进程，每个进程仍会留下 1 个热身代理；是否一并释放需要另定。
2. **直接使用 `ctx.agents.create()` 是本任务范围内的必要设计。** 只有调用方能拿到公开 `AgentHandle`；`sessionController.create()` 不提供句柄，rc.5 也没有按 id 释放接口。为了保持题会话的默认预设和模型选择，`createExam()` 复用了公开的预设 registry 并用原 `sessionController` 继续 prompt。建议复核方确认这条装配路径可接受。
3. 旧、新前 8 题对比不是严格同代码 A/B：旧数据来自 `V071-REG` 正式回归，新运行的 8 题为了遵守任务要求没有设 `BENCH_ENTRY_ROOT`。代码侧差别只有本批基准执行器改动，但旧运行还包含随后完成的 80 题。代理数和每题释放状态是直接观测；卡顿对比只作为小规模旁证。
