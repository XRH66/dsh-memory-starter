# 任务单 F：新对话第一句就带上短期接续（2026-11-14）

## 问题（Claude 已查实）

短期接续（`lib/handoff.js` 的 `selectHandoff`，由 `lib/index.js` 的 `onRequest` 注入）只在会话的第一个表面节点已经是 DSH 系统提示（`hasProtectedSystemHead`）时才会写入；否则记为 `deferred`，推迟到下一回合。

真实 DSH 的顺序是：`onPreStep` → `step/start` → `onRequest` → DSH 写入 `system/message`（`source.kind: 'system-prompt'`）→ DSH 把 `onPreStep` 返回的 `messages` 逐条写成 `user/message`。见 `test/handoff-head-replay.test.js` 的夹具，以及 N 批真实运行（`.local/benchmark-cmb/runs/2026-11-14T00-08-19-515Z-N-P01-full`）：

- 新会话第一回合执行到 `onRequest` 时，系统提示还没写入，所以**每个新对话的第一句都拿不到接续**，第二句才补上；
- 只读会话只在第一回合尝试一次（`index.js` 约 618 行），所以只读会话永远拿不到接续；
- 测试实例的接续状态里，续接历史会话第 1 回合为 `required:true, ready:false`，回合报告为 `deferred`；88 个考试请求的 `handoffChars` 都是 0。

用户在新对话里说的第一句，往往就是接着上一个对话问的，所以这是日常可感知的缺陷，同时也让单句考试完全测不到接续。

## 目标

新对话的第一回合（包括只读会话的第一回合），只要按现有规则需要接续（`first-use` 或 `conversation-changed`），就在**同一次模型请求**里带上接续材料。同时满足：

1. 接续消息位于系统提示**之后**，绝不能排在它前面；
2. 写入后保留在会话里，后续回合不改动已有前缀，以保护前缀缓存；同一对话只保留一条接续（沿用现有"同一对话只保留一条"的语义，以及 `lastDelivered` / `unchanged` 逻辑）；
3. 不重复：第一回合已经送达，第二回合不能再补一条；
4. 会话已有系统头时（同一会话内换模型、上次回答未完成等），继续走现有的 `onRequest` 路径，行为不变；
5. 记忆关闭、未授权、`recentContext === false`、非根智能体（子智能体）时，都不注入；
6. 落盘的会话文件仍能通过 DSH 严格回放（现有 `strictReplay` 测试）。

## 建议方案（实现前先在真实 DSH 隔离实例上验证假设；如果发现更好的办法，写进回执说明理由）

`onPreStep` 返回的 `messages` 由 DSH 在系统提示之后写入，预取就是靠这条路在第一回合生效的。所以：

- **第一回合、还没有系统头时**，在 `onPreStep`（`payload.step === 1`）里选出接续（`selectHandoff`），作为一条 `user/message` 放进返回的 `messages`。消息使用现有的接续来源标记（`source.kind: MEMORY_HANDOFF_SOURCE`，`form: 'handoff'`），并预先生成消息编号，记进回合状态（`state.handoffMessageId`，以及一个表示"由 onPreStep 送达"的标记）。
- 在 `onRequest` 里照常调用 `handoff.begin(...)`。如果该回合已经由 `onPreStep` 送达，就用这个消息编号记 `prepared`，并标记 `delivered`，不再 `deferred`，也不再追加第二条。如果 `begin` 判定不需要接续（理论上新会话第一回合不会出现这种情况），就用现有的 `expireHandoffMessages` 撤掉这条预放的消息，并在回执里说明。
- **位置**：优先放在本轮用户原话**之前**，即紧跟系统提示，顺序为"系统提示 → 接续 → 用户原话 → 预取 → 规则"，这样最符合"先看前情，再看本轮"的阅读顺序。如果 DSH 不接受改变用户原话的位置（例如校验失败，或者原话必须排第一），就放在用户原话之后、预取之前，并在回执里写明实测依据。
- 只读会话走同一条路径，但不写接续完成状态（遵守 RO 批的写入抑制）。
- 接续材料和预取都要算进现有的上下文上限，不能挤掉用户原话。
