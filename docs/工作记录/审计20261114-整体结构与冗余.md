# 审计：整体结构与冗余（2026-11-14）

只读审计，没有改产品代码。依据是 `10d0c50` 时点的 `lib/` 引用关系、各模块大小、测试与发布清单，以及 11-14 的 P01 测试记录。前提（用户已确认）：整体要简化；用户基本不在 Obsidian 里写东西；查看记忆改用从原话库和已保存内容生成的可视化页面。

## 二、对准确率、速度、费用没有正向作用的部分

| 部分 | 证据 | 建议 |
| --- | --- | --- |
| 整理层（12 类条目、整理模型、待确认、更正建议） | 开着时 P01 低 8 分，测试时间翻倍，每次搜索中位耗时从 1.1 秒涨到 2.35 秒；条目占搜索结果 30%，还和原话重复 | 整层去掉（顺序见第六节） |
| 每回合的"记忆控制说明" | 每回合都附一段关于 `soften_memory`、`dafeiyu_records` 的说明（约 260 字）；真正有用的回答规则反而只跟着预取走 | 和回答规则、本地时间合成一条短消息，每回合都附 |
| 向量"部分完成"误报 | 候选数达到上限被算成降级（`storage/profiles.js` 的 `examined < ordered.length`）；110 次搜索里有 99 次带着"部分检索没有完成"的提示交给模型 | 修判断：到上限不算降级 |
| 按类型的遗忘速度、弱化与强化的条目部分 | 测试最长只隔 45 天，看不出作用；依赖整理层的类型 | 随整理层去掉；"别再提"改成对原话降权 |
| 旧记忆迁移（`legacy-import.js` 36KB） | 要调用整理模型分 12 类，目标格式正是要去掉的条目 | 由"继承标准"取代 |
| 旧笔记通道、结构化条目通道 | 关掉整理后每次搜索都空跑（约 5 毫秒），代码却要维护 | 旧笔记导入原话库后去掉 |
| Vault 监视（`memory-vault-watch.js`） | 只为同步 Obsidian 里的手改；用户不在 Obsidian 写东西 | 去掉 |

## 四、结构问题

1. **`lib/index.js` 太大**（53KB）：一个文件里同时放了钩子、预取、接续、整理流水线、待确认、旧记忆迁移、文档管理、运行时切换。改任何一块都要碰它，这也是测试里"改一处牵连多处"的原因。整理层去掉后，它应该缩成"钩子 + 预取 + 接续"。
2. **`lib/client.js` 一个文件 147KB**：设置页全部界面挤在一起。整理模型、条目、待确认、旧记忆迁移这几页可以整块删掉。剩下的建议按页拆开：记忆开关、向量和重排、维护、状态。
3. **`deployment-config.js` 46KB**：安装、首次配置和运行配置混在一起；首次配置强制要求填整理模型（`bootstrap-host.js`），整理层去掉后要一起改。
4. **主观笔记 `records.js`（45KB，工具名 `dafeiyu_records`）**：这是人设自己的日记、想法、图库和人物印象，存成 Vault 里的 Markdown。它不属于记忆核心，又依赖 Vault。要由用户决定：留着就改存进原话库那一侧的 SQLite，在可视化页面里显示；不用就去掉。
5. **本地向量模型那一套**（下载、Python 编码、常驻时段、4B/0.6B 模型、按模型分档案）：日常已经用云端向量。它对离线和隐私有意义，但代码量大、测试多。建议降为可选组件，默认不装。
6. **测试脚本有两套，结果不一致**：旧脚本 `bench.mjs` 和新脚本 `bench-normal.mjs` 测同一份代码，差 4 分；新脚本里预取大多落空（正在查，见第五节）。最终只应保留一套，而且要和日常行为一致。
7. **测试依赖实验目录**：基准部署里的向量缓存路径指向 `.local/qqbridge-lab/...`。`.local/` 下有约 60 个早期实验目录，应归档，并把基准要用的缓存挪到基准自己的目录下。
8. **排队脚本编码**：不带 BOM 的 `.ps1` 被 Windows PowerShell 5.1 当作本地编码读，写进 `queue-status.txt` 的中文会乱码，等待脚本永远匹配不上。以后状态行一律用英文，或者存成带 BOM 的 UTF-8。

## 五、必须保留的核心（有正向证据）

原话库（`raw-rag/store.js`、`messages.js`、`query-reader.js`、`lexical.js`）、全文加向量搜索、重排、回合开始预取、三个记忆工具（`memory_search`、`memory_open`、`memory_recent`）、时间标注、回答规则、短期接续、只读会话、删除原话、对话开关与授权（`session-memory.js`、`memory-policy/`）。

证据：有预取的题正确率 74–79%，没有预取的 51–61%。旧脚本一题一题考时，90% 的题带上了预取；新脚本里只有 35–44%，原因正在用完整 88 题、并发 4 的测试查（这次会记下每次预取的结果和原因）。30 题的小规模探测里（同一时刻基本只有 1 题在考），26/30 带上了预取，被门槛挡掉 4 题，没有超时。

## 六、精简后的样子与顺序

精简后的结构：原话库（含继承标准导入的旧笔记）→ 全文、向量两路搜索加重排 → 预取和三个记忆工具 → 时间、回答规则和控制说明合成一条每回合消息 → 可视化查看页面（时间线、人物和话题筛选、搜索、前后说法对照、删除和"别再提"入口）。

顺序（接 `方案20261114-减法准备-最小核心.md` 第六节）：

1. 查清预取落空并修好测试脚本（进行中）。
2. 答题侧一批：每回合附规则（和控制说明合并）、修"部分完成"误报、过滤一两个字的原话；跑 P01 验证。
3. 统计日常库（只计数），定继承标准，导入旧笔记并核对。
4. 去掉整理层、Vault 层、旧笔记通道、旧记忆迁移、条目通道，设置页对应页面一起删；首次配置不再要求整理模型。
5. 清理死代码和遗留命名（包名、标记文件、`suzu/`、`unified-*`、`dafeiyu` 改成可配置的人设名）；`index.js`、`client.js` 拆分。
6. 本地向量模型降为可选组件；主观笔记按用户决定处理。
7. 做可视化页面。
8. 文档按新结构重写；用最终版本跑 V 批。

## 七、需要用户决定的事

1. 主观笔记（人设自己的日记、想法、人物印象）还要不要。**11-14 用户决定：保留。** 做法：功能和 `dafeiyu_records` 工具照旧；存储先保持 Markdown 文件（文件本身不依赖 Obsidian），但要和条目、类型遗忘速度、待确认这些整理层的东西解开耦合；可视化页面里单独一栏显示；搜索时标成"人设自己的笔记"，和用户原话区分开。
2. 本地向量模型降为可选组件，默认不装，可不可以。**11-14 用户决定：可以。** 默认只走云端向量和重排接口；本地下载、Python 编码进程、常驻时段、按本地型号分档案这些移到可选组件里，首次配置不再出现。已经装了本地模型的用户照常可用，升级时不能被悄悄关掉。
3. 公开包名、安装标记文件、`dafeiyu` 这类改名，要考虑已安装用户的升级兼容，是否这一轮就改。
