# 任务单 D2：回合编号迁移的下游一致性（2026-11-13）

前置：D 批已提交（`57d8056`）。D 批为兼容 Node 22.19，把默认回合编号的分隔符从 `\u0000` 改成 `\u001f`，并在打开原话库时一次性迁移旧数据（`lib/raw-rag/store.js` 的 `migrateTurnIds`）。迁移覆盖了原话库内的 9 张表、`raw_controls` 和 `legacy_scope_views.turn_revision`。

Claude 复查后发现：**旧回合编号还保存在原话库以外的地方**，迁移后可能对不上。真实日常数据库会在下次部署时执行这次迁移，所以必须先收口。

## 已知的库外副本

1. **向量档案的文档锚点**：`lib/memory-documents.js` 第 61 行附近，把旧原话来源的 `ref` 存进 `anchor`。旧原话的 `ref` 带 `turnId`，见 `lib/raw-rag/query-reader.js` 的 `embeddingSlots` 和 `legacyPage`，以及 `storage:'legacy'` 的分支。向量命中后，会用这个 `turnId` 回原话库查找（`loadTurns`、`get`、`neighbors`）。迁移后，锚点里还是带 `\u0000` 的旧编号，可能查不到，导致旧原话的向量命中静默消失；或者被判为来源失效，触发重新编码。
2. **会话内已经返回给模型的引用**（`memory_open` 用的短编号背后的 `ref`）：只活在当次会话里，影响小，但也要能解析。
3. 其他地方请自行排查：凡是把 `turnId` 写进原话库以外的持久化位置（Vault 文件、向量索引库、状态文件、回执），都要列出来。

## 要求

1. **在读取入口统一规范化**：在 `lib/raw-rag/store.js` 导出一个 `canonicalTurnId(value)`，把字符串里的 `\u0000` 换成分隔符，其余不变。所有接收外部传入回合编号、再拿去查库的入口都先经过它，至少包括：
   - `loadTurns`；
   - `storedTurn`；
   - `markImportedVisible`；
   - `sourceState` 里的 `ref.turnId`；
   - 按回合查控制项的路径；
   - `query-reader.js` 里用 `ref.turnId` 查库的各处；
   - `scripts/raw-memory.mjs` 的 `--turn` 参数。
   原则是：旧锚点、旧引用、旧命令行参数，在迁移之后都能解析到同一条回合。
2. **不改向量索引里已存的锚点**，不新增第二套迁移。读取时规范化就够了；如果你发现某处必须改写持久化数据，停下来写进回执，交给 Claude 决定。
3. 确认迁移本身是安全的，并用测试锁住：
   - **事务性**：迁移中途出错时整体回滚，数据不变，下次打开时重试。可以用注入失败的办法测；
   - **幂等**：迁移标记写入后，再次打开不重复执行；
   - **主键冲突**：如果同一个库里，同一回合既有旧编号行、又有新编号行（例如用 D 批之后的代码写入过），迁移时的行为要明确：不能报错导致库打不开，也不能丢数据。写测试覆盖这种情况，并在回执里说明你选择的处理方式。
4. **端到端测试**（新增到 `test/raw-rag.test.js`，或者新建 `test/turn-id-migration.test.js`；新建的话加入 `release-files.json` 里测试文件对应的位置，如果测试文件不在白名单里就不用加）：
   - 用旧格式（`\u0000` 分隔）写入若干回合，建立向量档案（假后端），记下旧原话的向量命中；
   - 关闭后重新打开，触发迁移；
   - 同一查询的向量命中仍然包含这些旧原话，`memory_open` 或等价的 `get`、`neighbors` 能展开；
   - 迁移后不触发重新编码：假后端记录的编码调用次数不增加；
   - 迁移后重新导入同一份历史，回合数不变，不产生重复（`history.js` 的幂等）。
5. **回退影响分析**（只写进回执，不写代码）：如果迁移后把程序退回 0.5.0 或 0.6.0，旧代码按 `\u0000` 计算编号，哪些功能会受影响（历史重新导入、控制项、视图等）？影响多大？据此建议部署前是否需要单独复制一份原话库文件。
6. **性能**：在测试里构造 2 万个回合跑一次迁移，把耗时写进回执，只记录、不做硬断言。
