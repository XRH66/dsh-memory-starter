# 任务单 M：预取门槛定型、上下文精简与语气（2026-11-13）

前置：A、B、R、C、D 批已提交。本批合并原计划的 M（上下文精简）和 T（语气）两批，因为它们改的是同几个文件。

## 背景：R 批真实回放的结论（Claude 已分析，本批照此实施）

R 批用真实的硅基流动向量和重排回放了 714 题（人物 P01、P12、P14、P16、P17、P20）。结论：

1. **召回不是瓶颈**：工具检索前 10 条命中证据的题占 96.4%（未命中 26 题）。
2. **绝对重排门槛分不开证据和噪声**：证据候选的重排分 p25 只有 0.19，非证据候选 p75 为 0.20。现行 0.35 门槛让有证据的题只剩 85% 左右命中。
3. **相对门槛有效**：对每题的预取候选，只留重排分 ≥ 本题最高重排分 × 0.5、且 ≥ 0.02 的记录。Claude 用已保存的信号离线模拟（选择组 P01/P12/P14，验证组 P16/P17/P20，最多 3 条）：

| 方案 | 选择组保留率 | 选择组非证据占比 | 验证组保留率 | 验证组非证据占比 |
| --- | ---: | ---: | ---: | ---: |
| 无门槛（B 批之前，前 4 条） | 100% | 约 44% | 100% | 约 44% |
| 现行：绝对 0.35，最多 3 条 | 83.0% | 10.6% | 85.9% | 19.3% |
| **新：下限 0.02 + 相对 0.5，最多 3 条** | **97.9%** | **10.3%** | **96.0%** | **20.7%** |

   预先定的规则（保留率 ≥ 97% 中选非证据最少）选出的是"最多 2 条"；Claude 改用 3 条，理由：一半的题（332/701）需要两轮以上的证据，3 条能完整覆盖 194 题，2 条只有 158 题，而噪声只多几个百分点。
4. **上下文构成**：每个开了记忆的回合，插件固定附加约 1211 token：回答规则消息 290，三个工具定义 921，其中 `memory_search` 说明就有 463 token，因为它把整套回答规则又抄了一遍。
5. **语气问题**的来源：回答规则每回合都作为一条用户消息出现，并写明"本轮整个回答（包括闲聊、建议和续写）都要遵守"，其中有"说明这是建议、推测或新编的内容"、"直接说没有记录"这类要求，会把回复推向谨慎、带免责声明的助手口吻。

## 第一部分：预取相对门槛

文件：`lib/memory-query.js`（`selectPrefetch`、`PREFETCH_OPTION_DEFAULTS`）、`lib/config.js`、相关测试。

1. 新增配置 `prefetchRerankRatio`，数字，范围 0..1，默认 `0.5`。在 `config.js` 里和 B 批加的其他 `prefetch*` 配置一样处理：`DEFAULT_CONFIG`、zod 结构和 `numberInRange` 三处都要加。
2. `prefetchMinRerank` 默认值从 `0.35` 改为 `0.02`，三处同步改。它的意思变成"绝对下限"，用来挡掉重排模型判定为完全无关的记录。
3. `selectPrefetch` 在 `rerankApplied===true` 时的准入规则改为：
   - 先算 `top`：本次候选中，排除空文本、`historical` 和 `disputed` 之后，有限 `signals.rerank` 的最大值。
   - 记录准入的条件：`rerank >= minRerank*f` 且 `rerank >= top*ratio*f`。更正记录（`isCorrectionRecord`）的 `f` 为 0.6，其他记录为 1。
   - `reason` 的取值规则不变：更正记录靠 0.6 折扣才过线的，记为 `'correction'`，其余记为 `'rerank'`。
   - 选项名沿用现有写法：`settings.rerankRatio ?? settings.prefetchRerankRatio`，取不到时用 `PREFETCH_OPTION_DEFAULTS.rerankRatio`（0.5）。
4. 重排没有执行时的回退规则（词面、向量、双路一致）**不改**，相关默认值也不改。R 批里重排 714 次全部成功，没有数据支持调整这些值。
5. 排序和截断不变：准入后仍按原有顺序做折叠和文本去重，最多 `maxRecords` 条、`maxChars` 字。
6. 测试（加到 `test/prefetch-noise.test.js`）：
   - 候选重排分为 [0.9, 0.5, 0.3, 0.01] 时，只准入前两条：0.3 低于 0.45，0.01 低于下限；
   - 全部候选都很低，例如 [0.04, 0.03, 0.015] 时：相对线是 0.02，下限也是 0.02，所以 0.04 和 0.03 准入，0.015 不准入；
   - 更正记录的 0.6 折扣同时作用于下限和相对线；
   - 被排除的 `historical` 记录即使分最高，也不参与 `top` 的计算；
   - 配置非法值（负数、大于 1、非数字）落回默认值。
   现有测试中依赖 0.35 默认值的，按新默认改写断言，但不得删掉测试覆盖的场景。

## 第二部分：回答规则跟着记忆材料走，语气中性化

文件：`lib/memory-query.js`（`ANSWER_RULES` 和工具说明）、`lib/index.js`（`makeAnswerGuidanceMessage`、`prefetchMessage`、`onPreStepInner`）、`lib/handoff.js`（接续消息的头尾文字）、相关测试。

1. **重写 `ANSWER_RULES`**，内容如下（可以微调措辞，但不能丢掉任何一条约束，也不能加长）：
   - 这些规则只管事实从哪里来，不改变你的身份、语气和说话方式
   - 只把记录里实际写到的内容当事实说；记录没写的具体时刻、日期、数字、地点、人物近况、别人的反应或原话、事情的后续和原因，不要自己补
   - 计划、打算、约定没有后续确认，不说成已经发生
   - 说时间以记录标注和当前本地时间为准，不取整、不估算
   - 同一件事前后说法不同，以最新的为准，并顺带点明之前的说法；记录没说原因就别替它找原因
   - 不翻出与当前话题无关的旧事，不主动谈第三方的健康、婚姻、家庭、经济等私事
   - 没有依据时，像平常聊天一样说不记得或没听说过，不要说"根据记录""记忆库"之类的程序用语
   - 建议、推测和续编照常发挥，不用每次声明，只是不能把它们说成记录里发生过的事
2. **规则不再每回合单独发一条消息**。改成跟着记忆材料一起出现：
   - 预取注入时，把规则附在 `<memory_prefetch>` 块里，放在材料行之后、结束标签之前，开头用一行"使用以上材料时："；
   - 接续消息（`lib/handoff.js` 的 `<memory_handoff>`）出现时，同样在材料之后附上这组规则。接续消息头部原有的"计划、打算不等于已经发生"等说明，和规则重复的部分删掉，避免说两遍；
   - 两处共用 `ANSWER_RULES`，不要各写一份。`handoff.js` 如果不方便从 `memory-query.js` 引入，就把 `ANSWER_RULES` 移到一个两边都能引入、又不形成循环依赖的模块里，例如新建 `lib/answer-rules.js`，`memory-query.js` 再重新导出它，保持现有导入不坏。
3. **当前本地时间**仍然每个开了记忆的回合都给，但改成极短的一条消息，例如 `<memory_clock>当前本地时间：…</memory_clock>`，`source.kind` 沿用 `'memory-answer-rules'`，以免改动过期清理逻辑。不再出现"本轮整个回答（包括闲聊、建议和续写）都要遵守"这句话。如果过期清理是按 `source.kind` 识别的，确认新消息和带规则的预取消息都仍会在下一回合被清理。
4. **`memory_search` 工具说明精简**：
   - 删掉拼接进去的 `ANSWER_RULES`，换成一句"只把结果里实际写到的内容当事实；本轮如附有记忆使用规则，照规则回答"；
   - 其余内容保留含义、压缩措辞：什么时候查、闲聊和通用建议不查、先做一次聚焦搜索、label 的含义、需要核对时用 `memory_open`、标有 correction 的最新更正优先、搜索结果大约 1K token 且可能不全；
   - 目标：说明部分从约 463 token 降到 200 token 以内。用 `lib/token-estimate.js` 或项目现有的估算函数在测试里断言上限。
   - `memory_open`、`memory_recent` 的说明不改。
5. **淡化策略消息**（`makeControlPolicyMessage`）不改。
6. 测试：
   - 没有预取、也没有接续时，本回合只附加时间消息，不再出现规则全文；
   - 预取注入时，规则在 `<memory_prefetch>` 块内且只出现一次；
   - 接续消息出现时，规则在 `<memory_handoff>` 块内；预取和接续同回合都出现时，规则允许各带一份，但同一块内不重复；
   - 下一回合，上一回合的时间消息和预取消息都被清理（已有过期测试改成覆盖新消息形态）；
   - `memory_search` 说明不包含规则全文，估算 token ≤ 200；
   - 规则文字里不出现"包括闲聊"、"说明这是建议"这类会推向助手口吻的说法（用断言锁住）。
   现有测试中断言旧消息文字的，按新形态改写，保留它们覆盖的场景。
