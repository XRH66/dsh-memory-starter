# 任务单：拆分整理费用和答题费用（2026-11-11）

执行者：Codex。设计与验收：Claude。

## 为什么做

准备参加一个记忆系统比赛：成绩和费用一起排名，每次封存跑最多 ¥50，超了不计分。比赛规模远大于我们的本地测试：

- 短对话榜：一个话痨用户，半年约 7000 轮短消息；
- 长对话榜：一个写长信的用户，半年约 5400 轮；
- 本地 r5 每个人物只有约 388 轮、70～120 道题。

需要搞清楚现在的钱花在哪：导入历史时的「整理」花多少，「答题」花多少，各自随什么增长，再推算到比赛规模。这是只读分析，不改系统。

### 账本注意事项（很重要）

- `days` 下按日期记账。同一笔费用会在**日级字段**、`byProviderModel`（按模型）和 `sessions`（按会话）三层**各记一遍**。只能用其中一层，绝不能三层相加，否则会算成约 4 倍。本次统一用 `sessions` 这一层，并和日级合计核对，两者应相等。
- 会话 `id` 分两类：
  - `session-bench-<人物>-history`：导入历史期间的调用，也就是**整理**；
  - `session-bench-exam-<人物>-<题号>-<随机后缀>`：**答题**，题号里的 `/` 换成了 `-`，例如 `P01-CASE-003/d00` 对应 `session-bench-exam-P01-CASE-003-d00-z7mab`。
  - 如果出现第三类会话，单独列出，不要并进前两类。
- `cost` 是按标价折算的美元，`costCny` 是人民币。日常线路走的是订阅，`apiCost` 为 0，这一点在报告里注明。另外照样报出输入、输出 token 数，方便以后按比赛的价格重新换算。
- Claude 已手工核对过：P01 合计 0.501 美元（210 次调用），其中整理 0.175 美元（68 次），答题约 0.326 美元。脚本结果必须和这组数对上。

## 要算的东西

1. **总拆分**：每个人物的整理、答题、合计，分别给出调用次数、输入 token、输出 token、美元、人民币。另加五人合计一行。
2. **整理**：
   - 每轮、每千字（按 `history.jsonl` 里的用户和助手正文字数）的整理费用；
   - 输出 token 在整理费用里占多少（输出比输入贵）；
   - 按日期看，整理调用次数和当天导入的轮数、字数是什么关系：是一天一批，还是按字数分批。
3. **答题**：
   - 每题费用、调用次数、输入 token 的分布（中位数、90% 分位、最大）；
   - 输入 token 看起来有两档（约 7.7k 和约 20k），用 `exams.jsonl` 的 `steps`、`calls`、`results` 查清两档分别是什么情况造成的，比如有没有调记忆检索、检索了几次、带回多少条；
   - 把每题费用和是否通过（`judgments.jsonl`）、间隔天数对上：通过题和失败题、不同间隔的平均费用和调用次数有没有差别。
4. **推算到比赛规模**：
   - 根据 `history.jsonl` 用户消息的平均字数，把五个人物分成「短消息」「长消息」两类（报告里写明分法），各自算出每轮的整理费用；
   - 短对话榜按 7000 轮、长对话榜按 5400 轮推算整理费用，给出一个范围（用最低和最高的人物）；
   - 比赛题数不知道，答题费用按「每 100 题」给出；
   - 写明推算假设：整理费用随轮数或字数线性增长、价格用本地标价。另外列出可能不成立的地方，例如记忆库变大以后答题检索带回的内容会不会变多。
