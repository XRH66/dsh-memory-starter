- 官方把思考和回答放在同一条 `assistant/message` 中，内容块分别为 `reasoning` 和 `text`。

- 所有导入助手消息都带有：

同一个 ZIP 再通过官方路由导入一次，仍返回 HTTP 200、3/3 成功。第二次返回的 3 个会话 id 与第一次完全不相交，并全部登记到同一工作区：


结论：官方功能不去重；重复导入会产生重复标题和重复正文的会话副本。

## 5. 发现的缺口和建议

### 5.1 裸 UUID 与补导工具不兼容

官方导入返回并落盘裸 UUID，普通 rc.3 会话使用 `session-...`，而 `history.js` 只接受后者。结果是官方功能本身可导入、会话文件也可严格恢复，但正式原话补导入口在预览阶段直接失败。

建议由 Claude 决定：

1. 放宽补导工具的原生 id 校验，使其同时接受官方导入 UUID；或
2. 由官方导入路径统一生成 `session-...` id；或
3. 在补导入口增加明确、可审计的 id 适配层，并保存原 id 到适配 id 的映射。

本次没有改代码，也没有把临时镜像方案说成正式兼容。

### 5.2 原话库没有独立保存来源

导入会话的助手事件有 `deepseek-chat-export` 来源，但 `completedHistoryTurns()` 只提取正文；原话库消息最终只有：

```text
id, role, speaker, text, ts, seq, docStart, docEnd
```

没有 `source`、`provider`、`origin` 或 `import` 字段。轮次级只有 `session_id`，必须依赖外部会话索引才能反查来源。因此“每条能不能看出来源”的当前答案是：不能只凭原话记录独立判断。

`buildTurn()` 已能透传 `message.import`，但当前历史提取没有填这个字段。可考虑在提取阶段把助手事件的 `deepseek-chat-export` 映射成明确的导入来源元数据。

### 5.3 助手时间包含思考耗时

官方行为符合其 README：思考 `elapsed_secs` 计入后续 step。原话库因此保留的是导入事件时间，而不是导出回答的原始 `inserted_at`。若以后需要严格还原“回答原文时间”，仅靠当前消息 `ts` 不够，需要额外保留导出原始时间。

### 5.4 重复导入不去重

官方重复导入会生成新会话；原话库按新的会话 id 也会形成另一组来源。以后若要避免重复，需要在导入会话层或原话补导层增加来源导出 id、会话稳定指纹或显式去重策略。本批未实现。

### 5.5 缺失或未覆盖

- 本批只测普通文本、思考、两轮问答和分支；未覆盖图片、文件卡片、联网搜索、网页抓取、内容过滤、失败回答和取消导入。
- 未使用真实 DeepSeek 导出文件；所有结构均由虚构数据和官方类型构造。
- 未运行全量测试；任务单明确不要求。
