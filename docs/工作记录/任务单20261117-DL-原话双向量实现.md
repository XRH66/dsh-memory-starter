# 任务单 2026-11-17-DL：原话双向量（带背景＋只正文）实现

工作区：仓库主目录。执行方按本单实现，不提交。

## 背景

DK 批（`回执20261117-DK-预取漏召回修法对比.md`）测得：原话编码时把前文拼进去，会冲淡短句的意思，是自动预取漏召回的主因。用户 11-17 定采用 **V3 双向量**：每条原话存两份向量，一份带背景（现状），一份只编码正文；查询时同一条原话取较高相似度。两份语料上，V3 自动预取 68/95 → 76/95，主动搜索 82/95 → 94/95，无答案误注入不变（15 题 / 16 条）。

DK 的 V3 变体代码在 `.local/prefetch-fix-20261117/variants/V3/lib/storage/profiles.js`（第 531～550 行附近，相对现状只改了这一处），是测量用的最小改动，**不能直接照搬**，要补齐下面的生产要求。

## 要做

1. **双份编码**：原话（`domain === 'raw'`）**确实带了背景前缀**时，同时编码"带背景"和"只正文"两份分块；没有背景（对话第一条等）时只编码一份，不要重复编码同一段文字。人设笔记、手选资料等其他来源不变。
2. **已有索引自动重建**：升级后，已经建好索引的原话要自动按新方式重新编码一次（例如提升 `lib/raw-rag/embedding-material.js` 的版本号，或现有机制里更合适的办法——先读代码确认版本/指纹变化是否真的会触发重编码）。重建只进行一次；重建期间检索照常可用（旧向量可用或退回全文都行，以现有机制为准，回执写明实际行为）；不得删除原话正文或队列。
3. **查询按原话去重取最高**：确认并保证同一条原话的两份向量在向量通道里**只算一条候选、取较高相似度**；向量通道上限（`VECTOR_LANE_LIMIT = 10`）按不同原话计数，不能因为一条原话占两个位置而挤掉别的原话。预取、主动搜索、展开、近期原话等使用向量结果的地方都要核对。
4. **删除与淡化**：删除某条原话、修订原话、撤销授权等现有会移除向量的路径，要把两份都移除；淡化/遗忘强化行为不变。
5. **状态页**：索引进度和条数显示要合理（按原话计数还是按分块计数，以现有口径为准；如果数字会翻倍让用户误以为出错，写进回执给 Claude 定，不要自己改界面文案）。
6. **测试**（`test/` 下，用临时目录和假向量后端）：带背景时编码两份、无背景时一份；旧版本索引升级后重编码一次；同一原话两份向量在检索结果中只出现一次且取高分，向量通道上限按原话计数；删除原话后两份都没了；其他来源不受影响。
7. **复测**：在 `.local/prefetch-fix-20261117/variants/` 新建 `DL/`，把改好的仓库 `lib/` 复制进去，用 DK 的 `measure.mjs` 在两份冻结语料上各跑一次（只允许 `bge-m3`、`bge-reranker-v2-m3`），结果应与 DK 的 V3 基本一致（语义预取 76/95 左右、主动搜索 94/95 左右、字面 40/40、无答案误注入不升）。不一致要查明原因写回执。
8. 估算日常规模下重建的代价：按每条原话编码次数和平均 token 写出公式即可，**不读真实记忆库**。
