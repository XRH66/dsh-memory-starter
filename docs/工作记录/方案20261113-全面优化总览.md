# 全面优化总览（2026-11-13）

负责：Claude 主导设计和验收；Codex（`ccs-opencode-3/deepseek-v4.1-flash`，max 档）按任务单实施。用户已确认：允许结构性重构，Node 22 要修兼容，付费调用按需可用，推送、打标签、部署日常 DSH 在全部完成后一次性请示。

目标排序：**检索噪声 > 速度 > 局部缺陷 > 兼容 > 结构精简**。所有改动保持现有核心行为（按对话授权、原话由程序保存、短期接续、后台整理、遗忘曲线、更正与历史、向量档案、删除原话、旧记忆迁移）。

## 一、代码核查得出的结构性问题

### 速度

1. **"四路并发"在文字通道上是串行的。** 原话全文、条目和旧笔记三路都用同步读取（`node:sqlite` 的 `DatabaseSync`、`fs.readdirSync`/`statSync`/`readFileSync`），在主线程上依次跑完。真正异步的只有向量通道。
2. **向量请求最后才发出。** `runMemoryQueryLanes` 按对象键顺序启动通道，`vector` 排最后；它的第一个 `await` 之后，三路同步文字检索会先占满主线程，查询编码请求要等它们跑完才发出。使用远端向量接口时，这段网络耗时本可以和文字检索重叠。
3. **旧笔记缓存每轮重建。** `createLegacyNoteReader` 的缓存挂在每次 `createMemoryQueryAnswer` 上，而预取和每个回答都会新建一次，所以每轮都会重新读全部旧笔记、算 SHA-256、重新分词。`legacyImportFingerprints` 每次检索也都重新读状态文件。
4. **向量候选被核对三次。** `profiles.query` 返回前已经逐条回源复核；`memory-query.js` 融合后又跑一轮 `resolveDocument`（最多 200ms 预算）；`validateResult` 打包时还要再核一次。
5. **向量排序逐元素调用 `readFloatLE`。** 每次查询都要把全部向量块从数据库读出来，再逐个元素解码。
6. **寒暄也会预取。** "好的""继续"这类输入照样跑完整检索，最坏要等 1.5 秒才发出模型请求。

### 噪声

1. **没有绝对相关度。** 融合用的是倒数排名，`1/(60+名次)` 乘以重要度等权重，只能排序，没法判断"够不够相关"。词面覆盖率和向量相似度两个绝对信号在融合时都被丢掉了。
2. **按"条目编号 + 版本"去重，不按事件去重。** 已经整理成条目的原话、内容相同的旧笔记，会各占一个预取槽位。
3. **旧笔记显示成"记忆条目"。** 模型看不出它是没迁移、没核对来源的旧格式内容。
4. **预取放在最后。** 消息顺序是"用户原话 → 回答规则 → 淡化策略 → 预取"，预取离生成位置最近，模型最容易受它影响。旧原话里的问句也会被模型当成待回答的问题。
5. **淡化策略消息过时。** 这条消息每轮都附带约 1000 字英文，其中还提到 Basic Memory 时代的 `write_note`/`edit_note`/`move_note` 工具。
6. **技术错误被模型原样转述。** 后端报错时，模型会对用户说"记忆后端暂时无法返回有效结果"。

## 二之一、速度原则

提速不靠缩短超时或减少检索范围，而是减少不必要的工作和等待：

- 同步工作不阻塞异步请求；
- 缓存不每轮重建；
- 不重复核对；
- 整理不卡在关键路径上；
- 能并行的并行。

现有时限（预取 1.3/1.5 秒、工具检索的等待预算）保持不变。时限只作兜底，正常情况下不应该被触发。基准测试的全卷耗时，按题库作者所说的约 2 小时作为量级参考。我们的评测侧重和他们不完全一样，不强求对齐。

## 二之二、语气：记忆规则把回答推向"助手腔"

现状：开启记忆的每一轮，都在用户原话后面附上 `<memory_answer_rules>`，作为用户角色的消息，紧挨着生成位置。它的作用范围写的是"本轮整个回答（包括闲聊、建议和续写）都要遵守"。同样的规则还在 `memory_search` 的工具说明里再出现一遍。规则内容偏防御性，比如：

- "只回答被问到的事"；
- "建议、推测要说明是建议、推测"；
- "记录里没有就说没有记录"。

再加上检索结果标签"原话 · 用户说 · 时间"，模型容易出现以下问题：

- 闲聊也带免责声明；
- 动不动说"根据记录""记忆库里没有"；
- 语气从人设滑向通用助手；
- 规则离生成位置最近，压过系统提示里的人设。

方向（T 批，具体任务单在 M 批测量之后写）：

1. **规则只管"过去的事实"，不管语气。** 明确写出"不改变你的人设、语气和说话方式"。
2. **自然表达。** 回答里不提"记录""记忆库""检索"，像本人记得一样自然地说；记不清时，用符合人设的说法表达不确定。
3. **作用范围收窄。** 只有本轮实际带了记忆材料（预取、接续或工具结果）时，才附上完整的事实规则；纯闲聊回合只保留一句最简提醒，或者完全不加。是否保留，由测量结果决定。
4. **合并与去重。** 规则和预取合成一条消息，总字数减少；工具说明里不再重复全文规则。
5. **验证。** 准确性和语气都要验：
   - 准确性：P01 答题分不低于旧基线，编造日期这类错误不增加；
   - 语气：一组虚构的人设闲聊和回忆题，新旧两版各答一次，由判分模型盲评"人设一致性"和"助手腔"。判分模型调用量小，属于按需付费。

### "闲聊回合"怎么判断：不用模型分类

不另调模型判断意图：那样每轮多一次调用，既增加延迟又花钱，而且也会判错。改用程序在本轮已经掌握的事实来区分：

| 本轮情况 | 附加内容 |
| --- | --- |
| 预取有记录通过门槛，或本轮注入了短期接续 | 完整的事实规则 + 记忆材料（一条消息） |
| 用户原话命中"回忆意图"句式（复用 `lib/raw-rag/lexical.js` 里已有的 `RECALL_QUESTION` 等规则，例如"我有没有说过""你还记得"），但预取没有通过门槛 | 完整的事实规则，加一句"需要时用 memory_search 查，查不到不要编" |
| 以上都不是（闲聊、通用问题、寒暄） | 只留一句最简提醒，或者不加，由 T 批测量结果决定 |
| 模型主动调用记忆工具 | 规则随工具结果一起返回（写在结果信封里），不依赖每轮附加 |

最后一行是关键：规则跟着记忆材料走。模型看到记忆内容的地方，就有对应的规则；没有记忆内容的回合，就不被规则影响语气。

## 二之三、成本：每批都量，最后再核实

成本不留到最后才看，因为到那时已经分不清是哪一项改动带来的。成本由四块组成，分别在不同批次处理：

| 成本来源 | 在哪一批量和改 | 怎么量 |
| --- | --- | --- |
| 每轮回答的输入 token：接续、预取、规则、工具说明、历史 | R 批测基线，M、T 批精简 | 回放时按组成部分估算 token，不花钱 |
| 前缀缓存命中：每轮附加消息的过期替换会不会让缓存失效 | M 批 | 检查消息替换的位置，结合用量记录里的缓存命中字段 |
| 后台整理调用：每批输入、输出 token，合批大小 | S 批 | 整理器已有用量记录，按批统计 |
| 向量接口编码 | A、R 批顺带 | 次数 × 单价，量很小 |
| 测试本身的花费（P01、714 题、判分） | 每次运行前先报预估 | 按以往记录估算 |

每批的回执都要有"成本影响"一栏：每轮平均输入 token 的前后变化，以及整理 token 的前后变化。全部改完后，跑 714 题时再用真实账单核对一遍总花费。

## 三、度量

**新增离线测速脚本** `scripts/bench-prefetch.mjs`（A 批）：用虚构数据建 2000 轮原话、300 条条目、200 篇旧笔记，向量通道接一个可设延迟的假后端。报告：

- 预取 p50 和 p95 耗时；
- 向量编码请求发出的时刻（相对检索开始）；
- 各通道耗时；
- 旧笔记通道在缓存命中时的耗时。

**新增噪声回放测试**（B 批）：把虚构对话库和四类查询写成测试夹具，分别是明确回忆、隐含相关、无关新话题、更正敏感。断言以下几项：

- 无关话题不注入；
- 同一事件只占一个槽位；
- 更正后的新值排在旧值前面；
- 旧笔记带"旧笔记"标签。

数据全部虚构。只测通用规则，不针对任何基准题调参。

## 四、明确不做

- 不在预取链路里调用模型，包括改写、冲突检测和重排门槛。
- 不把预取移到系统提示前，以免破坏前缀缓存和过期清理。
- 不在写入时按相似度强行合并事件。
- 不读真实记忆库，不启动 QQ，不切 Suzu，不升级 DSH，不调用大肥鱼。
