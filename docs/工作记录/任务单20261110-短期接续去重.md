## 背景：现在怎么工作

「短期接续」在已开记忆的对话里、每轮第一步发请求时判断一次（`lib/index.js` 的 `onRequest`，约 486–516 行；`lib/handoff.js` 的 `begin`）。这次请求的「对话 + 服务商 + 模型 + 连接」与上一次不同（或首次使用、或上次没完成）就注入一条 `<memory_handoff>` 用户消息，内容是 `selectHandoff` 从最近保存的聊天原文里按预算挑出来的。

## 要解决的问题

1. **同一对话里的原文被重复带入**：`selectHandoff` 只排除「当前对话的当前这一轮」。在同一对话里换模型时，挑出来的大多是本对话更早的消息，而这些本来就在对话上下文里。
2. **来回切换会累积**：A 发一句、B 发一句、回 A 再发一句，每次都注入一条；旧的接续消息在记忆保持开启时不会被清掉（`expireMemoryContext` 只在 `includeHandoff` 为真时才清），于是同一个对话里越积越多，内容大半相同。
3. **子代理（待查）**：子代理的请求可能被当成「换了对话」，导致子代理自己被注入一次、主对话下一轮又被注入一次。

## 目标行为

- 接续内容**只包含其他对话的原文**，不包含当前对话自己的。
- 每个对话里**最多保留一条**有效的接续消息：要注入新的，就先把本对话里旧的接续消息换掉。
- 回到一个已经注入过的对话（或只换了模型）时，**如果其他对话没有出现新内容，就不再注入**，沿用还在上下文里的那条。
- 触发条件本身（首次、换对话、换 API、上次未完成）不改。开关、预算、消息格式、头尾文案不改。

## 代码架构

### 1. `lib/handoff.js` · `selectHandoff`

- 跳过条件由 `source.sessionId===sessionId&&source.turn===turn` 改为 `source.sessionId===sessionId`（整个当前对话都不选）。`!source.text` 的跳过保留。
- 返回值增加 `newest`：遍历中遇到的**第一条**符合条件（其他对话、有文本）的原文的 `{id,revision}`；一条都没有则为 `null`。它代表「其他对话里最新的那条原文」，与预算无关（即使那条被截断也算）。

### 2. `lib/handoff.js` · 状态

每个对话的 `entry` 增加 `lastDelivered:{messageId,newest}`，表示上一次真正送达的接续：

- `prepared(attempt,receipt,…)` 的 `receipt` 增加 `newest`，存进 `current.receipt`；
- `finish` 里，当本次 attempt `completed && ready && delivered` 且 `receipt.messageId` 非空时，写 `entry.lastDelivered={messageId:receipt.messageId,newest:receipt.newest??null}`；
- `begin` 的返回值带上 `lastDelivered:entry.lastDelivered??null`（取调用时已有的值）。
- 旧状态文件没有这些字段，必须照常可读（当作没有上次送达）。

### 3. `lib/context.js`

新增并导出一个小函数（例如 `expireHandoffMessages(session,{turn,step})`），把当前对话里**所有** `source.kind===MEMORY_HANDOFF_SOURCE` 的消息替换掉，做法与 `expireMemoryContext` 里对一组消息的替换完全相同（同样要求处在匹配的打开步骤里）。可以把 `expireMemoryContext` 里的公共部分抽出来共用，但不要改变它现有的行为和返回值。

### 4. `lib/index.js` · `onRequest`

在 `attempt.required` 且不是 `alreadyDelivered` 的分支里，流程改为：

1. `selected=selectHandoff(…)`（已不含当前对话）。
2. `live`＝`attempt.lastDelivered?.messageId` 对应的消息仍在 `session.deriveMessages?.()` 里。
3. **没有新内容**：`live` 为真，且 `selected.newest` 与 `attempt.lastDelivered.newest` 相同（`id` 与 `revision` 都相等）→ 不追加消息；`handoff.prepared(attempt,{messageId:attempt.lastDelivered.messageId,newest:selected.newest,tokens:0,items:0,…})`；`state.handoffMessageId` 设为那条旧消息的 id，`state.handoffDelivered=true`；`report(...)` 里 `handoff.state` 记为 `'unchanged'`（带 `reasons` 和 `generation`）。
4. **有内容要注入**（`selected.text` 非空且不属于第 3 条）：先调用第 3 节的函数清掉本对话里旧的接续消息——用 `try/catch` 包住，失败只 `logger?.warn?.('[memory-handoff] replace: '+…)`，不影响后面的追加——再按现有方式追加新消息；`prepared` 的 receipt 带 `newest:selected.newest`。
5. **其他对话没有任何原文**（`selected.text` 为空）：沿用现有的 `'empty'` 处理，不清旧消息。
6. 原有的授权检查（`authorize()` 失败时 `revokePending()`）在每个分支里都要保留，顺序不要打乱。

### 5. 子代理（先查清再决定）

先读代码弄清：子代理（有上级的 agent）的请求会不会走到 `handoff.begin` / `handoff.observeTarget`，它的 `session.id` 与根对话是否不同。

- 如果会、且 id 不同：改成**只有根对话参与接续**——子代理的请求既不注入，也不更新比较基线（不调用 `begin`、不调用 `observeTarget`）。判断根对话用仓库里已有的办法（例如 `lib/session-memory.js` 的 `rootAgent`，或 `access` 上现成的接口）；需要的话给 `access` 加一个很小的只读方法。
- 如果不会、或共用根对话的 id：不改，在回执里写明依据（文件和行号）。
- 如果在这一层确实拿不到可靠的判断：不改，在回执里说明，不要猜。

### 6. 测试

现有 `test/handoff.test.js` 等用例里依赖旧行为的断言相应更新（例如「同一对话更早的原文会被选入」）。新增或改写的用例要覆盖：

1. `selectHandoff`：当前对话的原文一条不选；`newest` 是其他对话里最新一条的 `{id,revision}`；没有其他对话原文时 `text===''` 且 `newest===null`；预算、截断、转义的现有断言仍成立。
2. 状态：`finish` 成功送达后 `lastDelivered` 被记录，下一次 `begin` 能拿到；旧格式状态文件可读。
3. 集成（沿用现有覆盖 `onRequest` 接续的测试桩，先找到它在哪个测试文件）：
   - A 注入 → B 发一轮（产生新原文）→ 回 A：A 里旧的接续消息被替换，只剩一条有效的接续消息，内容包含 B 的新原文、不含 A 自己的原文；
   - A 注入 → 在 A 里只换模型、其他对话没有新原文：不追加新消息，报告状态为 `unchanged`，旧消息仍在；
   - A 注入 → 只切到 B 再切回 A 但 B 没产生任何可用原文：A 不重复注入；
   - 清理旧消息的函数抛错时，新消息仍然追加，且有一条警告日志。
4. 子代理：按第 5 节的结论补一条对应的测试（改了就测「子代理不注入、不影响主对话」；没改就不加）。
5. 最后跑一次全部单元测试，要求全部通过（当前基线 692 个）。若 `test/raw-device.test.js` 的显卡回退用例偶发失败，单独重跑该文件确认，并在回执里如实写明。
