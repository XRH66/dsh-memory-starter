## 1. 子代理所属关系兼容

### 采用的方案

新增 `lib/host-compat.js`，集中处理运行时代理归属：

- 有 `agents.isOwnedBy` 的宿主继续逐项调用该方法，rc.5 的正常路径和判定顺序不变。
- 没有 `isOwnedBy` 时，在 `agent/created` 发布期间调用 `agents.currentInitiator()`，只在以下条件全部成立时记录父关系：
  - `currentInitiator()` 返回的是另一个代理；
  - 子代理和父代理仍是 `agents.get(id)` 返回的同一个存活对象；
  - 父代理仍在当前 `agents.list()` 中。
- 关系存入独立的弱映射，不读取宿主的内部 `AgentRegistry.store`。
- 无法确认父关系时返回空父集合。子代理随后按独立对话处理，默认不获得记忆权限，也不会继承父对话授权。
- 对看起来是子代理但无法确认归属的对象只警告一次，不按对象刷屏。

`lib/session-memory.js` 不再把 `agents.isOwnedBy` 当成启动硬条件；根对话解析和 `lib/platform-host.js` 的工具作用域都使用同一个兼容对象，没有两套判断。

### 候选结论

- `agents.isOwnedBy`：rc.5 的可靠公开运行时归属接口，保留为首选。
- `agent/created` 的 `source`：rc.3 的代理循环在普通创建和恢复时传字符串 `startup` / `resume`，不携带父代理身份；子代理创建也走同一发布路径，因此单独使用 `source` 不能判断归属。
- `session.header.parentSession` 或派生会话来源：能表达持久化创建关系，但无法证明当前进程中的运行时拥有者，也可能把持久化分支误当成父代理。现有测试明确拒绝用 fork 谱系建立运行时授权，因此不采用。
- `currentInitiator()`：rc.3 在父代理发起的异步链内调用 `agents.create()`，`agent/created` 发布仍在同一 initiator 作用域内；这是本单采用的同进程因果关系。由于其文档明确说明“存在不等于存活或授权”，实现额外核验了精确存活对象。
- `AgentRegistry.store` 中的 `owner`：运行时事实存在，但属于内部存储结构，没有公开替代接口；不直接依赖，避免再次绑死宿主内部布局。
- `subagent` 管理器的树归属：只覆盖子代理插件自己管理的会话，还要求额外宿主服务和调用前提；不能作为所有代理的通用归属接口。

## 2. 关闭记忆时的工具可见性

### rc.3 源码结论

rc.3 的 `@deepseek-ai/dsh-system-prompt` 在瀑布前收集并排序工具，但传入 `system-prompt/assemble` 瀑布的组装对象只有 `sections`、`contexts`、`variables`，没有 `tools`。瀑布返回后，宿主才把保存好的 `tools` 合并回去。

因此：

- 我们在 `system-prompt/assemble` 里根据 `assembled.tools` 做的筛选在 rc.3 上不会报错，但会静默失效。
- 现有平台代码已经在每个代理的 `agent.ctx` 上探测并调用原生 `tools.restrict({deny})`；rc.3 的 `@deepseek-ai/dsh-tools` 提供同一作用域级限制接口，限制发生在工具 schema 进入模型请求之前。
- 本次没有改检索、工具描述或提示过滤规则。rc.5 继续保留原提示过滤；两个版本都依靠已经在用的原生作用域限制作为真正的工具可见性边界。
- 现有平台测试已覆盖“默认关闭时限制 `memory_*` 和旧 Basic Memory 工具、工具目录变化后刷新限制、关闭授权立即恢复限制”。本次这些测试均通过。

### 实机限制

rc.3 隔离实例可以正常加载插件，但模型目录 RPC 返回 `groups: []`，没有可用对话模型。按任务单要求，没有发送对话，也没有调用任何付费模型接口。因此本轮没有从一次真实无记忆对话的请求记录中枚举工具列表；第 2 项的结论来自 rc.3 宿主源码、当前走到的原生限制分支和相关测试，对话级实机枚举留待隔离环境有可用模型时补测。
