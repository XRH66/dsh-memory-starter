## 发现的问题

### 已修复（工作区，未提交、未部署）

1. **向量查询遇到换行或首尾空白就失败**（`lib/memory-query.js`）。向量服务的 `requiredText` 拒绝控制字符和首尾空白，返回 `INVALID_MEMORY_VALUE`，检索通道只显示"不可用"。受影响的有两处：模型的 `memory_search`（多行问题、带换行的查询），以及**后台整理查找相关旧条目**（原话带换行时语义参照失效）。修复：只对向量通道把查询折成单行；文字通道不变。新增回归测试，全量 1056 项：1054 通过、2 项跳过、0 失败。

2. **（夜间追加）后台整理输出被截断，失败的批次永久滞留**（`lib/memory-organizer.js`、`lib/memory-pipeline.js`）。新版整理沿用了旧版逐轮提炼的输出上限 `captureMaxTokens`（默认 8192，配置上也封顶 8192），而一次整理覆盖一整批多轮对话，推理模型的思考也计入这个上限。真实测试中一批 9 条条目就输出了 7677 token，17 轮一批则截断（`MEMORY_OUTPUT_TRUNCATED`），连续重试 3 次失败后批次标为 `error`。更糟的是，批次里的任务被改回"待处理"却仍挂着失败批次的 ID：打包新批次时会跳过它们，状态也看不出失败，**那部分对话永远不会整理成长期记忆**，"等待整理完成"也会一直等下去。
   - 修复：整理器使用独立的 `organizerMaxTokens`，默认 32768；`captureMaxTokens` 仍只给旧版逐轮提炼使用。批次耗尽失败后，任务改标为"搁置"并记录失败原因，保留批次 ID，仍然不会自动重试（原有设计和测试保持不变），但状态里能看出失败。
   - 新增测试 2 项，全量 1057 项：1055 通过、2 项跳过、0 失败。真实模型复验（P01 前 50 轮、4 题）：5 批全部提交，第一批输出 11846 token，没有任务滞留，考前等待 16–90 秒，费用约 ¥0.37。

### 已确认、待修复

2. **向量通道耗时随资料量线性增长。**40 轮时已从 258 毫秒涨到 763 毫秒，而检索预算是 2 秒。全卷每人约 390 轮，预计会超时降级。原因很可能是对前排候选逐条核对来源（每条都要经 MCP 读笔记并读盘校验）。待用正式卷的真实规模量化后再改。
3. **原文文字检索对整句提问几乎搜不到。**全文检索要求关键词都对上，"借了阿岑什么"搜不到"阿岑借我一把活动扳手"。按设计应由向量通道兜底；修复第 1 点后兜底已生效，但仍需看真实模型的检索词。
4. **撤回的消息仍留在全文索引里**，在 SQL 层不过滤，读取层才丢掉。目前每次多取 8 倍，影响很小，属于清理项。
5. **Basic Memory 每次写笔记都用内置 bge-small 额外编码，但 portable 不使用这份向量**（见性能测量记录）。

### 测试框架自身已修复的问题

- 逻辑时钟最初只能往前走，而数据集时间早于真实时间，导致时钟从未生效：整理只能干等 90 秒，模型看到的是真实日期。现在 DSH 启动前就设好起点。
- 考试时带 `clientTimeZone: Asia/Shanghai`，和数据集的 +08:00 一致。
- 旧的 session-memory-qa 验收脚本已过时（它的假模型只认旧版逐轮提炼），5 项失败对应 11-06 之后的有意设计变更，不再维护。

## 提速第 0、1 步（2026-11-09）

**第 0 步：框架全程计时。**`exams.jsonl` 新增 `steps`（save、settle、create、answer、agentProbe、withdraw、vectorProbe、memoryOff、total）。免费演练立刻查出：**每题约 90 秒花在考前等待"还没到期"的整理批次上**——d00 考题紧跟最后一轮，批次要等 90 秒空闲窗口才到期，框架却按真实时间干等。改为：在考试的逻辑时间点尚未到期的批次保持待处理（与真实使用一致），不再等待。免费演练每题总耗时 97 秒 → 7–17 秒。注意：此后 d00 题考的是"尚未整理"的真实状态，与之前各轮的等待口径不同。

**第 1 步：向量通道"不可用"。**查出两个真实缺陷（`lib/raw-rag/backend.js`、`lib/unified/profiles.js`）：
1. 编码队列满 16 个就直接拒绝新任务，**查询也一并被拒**，抛出无错误码的普通 Error，表现为 19 毫秒即返回 `VECTOR_QUERY_UNAVAILABLE`。整理提交后大批文档入队时，模型检索正好撞上。修复：上限只计维护任务，查询永不因队列满被拒；维护任务被拒时带 `EMBEDDING_QUEUE_FULL`。
2. 空闲释放计时器会在一次操作"准备好模型→解析候选→再编码/核对 modelKey"的间隙触发，把 identity 置空，导致 `EMBEDDING_IDENTITY_MISMATCH`（空闲 3 秒的演练中准备阶段即复现）。修复：`backend.hold()`，profiles 在持有后端期间不允许空闲释放。
3. 另：`memory-vectors` 的无码错误现在带 `detail`，不再吞掉原因。

模型空闲卸载后，下一次查询要重新加载（约 10–15 秒），超过检索 2 秒预算，仍会超时一次。这是 `rawRecallIdleMs`（日常配置 120 秒）的取舍，建议日常调大，未改默认值。

新增测试 2 项；全量 1062 项：1060 通过、2 跳过、0 失败（`unified-scheduler` 中一项偶发失败，单独重跑通过，与本次改动无关）。
