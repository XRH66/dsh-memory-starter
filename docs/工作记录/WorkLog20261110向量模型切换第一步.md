## 与方案不同之处及原因

1. **快照保留 5 份，而不是方案的 1 份**（用户决定）。因此 `test/unified-profiles.test.js` 的两条现有用例不必再改，已还原为与 `09cdb14` 完全一致（中途一度改成“先钉住旧快照”，现已撤销）。
2. **清理时保护的快照比方案多一类**：除了 active 和查询进行中的快照（引用计数），还保护"被非管理授权钉住的快照"（`pinSnapshot` 新记录 `indexId`）。原因是 `memory-query.js` 先 `getSnapshot` 再 `query`，两步之间如果快照被删，这次回答的向量路会降级。
3. **3.2 采用方案里的"退一步"做法**：`status()` 只给 `index.hasSnapshot`，"落后 N 篇"由 `plan()` 计算，界面打开时对所看模型调一次。没有做状态缓存，现有状态接口的耗时不变。
4. **字符数字段加在 `lib/memory-documents.js`**（清单实际在这里生成），不是方案写的 `memory-vectors.js`。除 `length` 外还加了 `cjk`（中日韩字数），因为方案的 token 粗估需要区分字符类别。两个字段都只是元数据，不参与 `sameDocument`，也不影响索引身份。
5. **3.3 没有按方案做等待**（用户决定）：后端行为与基线相同，有查询在途时准备立即失败、进度记为 `error: EMBEDDING_BUSY`；只在界面上把这个错误码换成中文提示，请用户等对话结束后再点。确认过的切换若因此失败，切换面板会显示同一提示和「重试」按钮。
6. **3.4 额外改了 `lib/config.js` 和 `lib/settings-host.js`**。确认标记要经过 `resolveConfig` 才能到达 `memory-vectors`，所以加了 `rawRecallSwitch`（只在内部解析，不是公开的打包参数）。设置页 HTTP 层有动作白名单，所以加了四个新动作，并只接受布尔值的 `cloudConfirmed`。
7. **意图"只用一次"的机制**：部署配置在重载时把 `pendingRawRecallSwitch` 落成 `memory.rawRecallSwitch`，这一项会留在部署配置里。为避免每次重启都重新生成意图，`profiles.json` 的作用域记录 `switchConsumed`（已用过的 `confirmedAt`），同一次确认只生效一次。
8. **界面不是"每张卡片"**：现有页面是"查看模型"下拉加一个运行面板，没有卡片，也没有现成的确认框。所以在所看模型下方加了 `ModelSwitch` 小面板，确认框做成页内的（没有用浏览器弹窗）。状态行文案按方案表格；另外 active 档有待补内容时显示"使用中，需补 N 篇"。
9. **「恢复上次向量设置」的确认框不显示篇数预估**，只说明会自动补齐、只编码变化部分。历史项对应的档位不一定已登记，预估要等重载后才能算。

## 没有做或没有覆盖的

- `lib/index.js` 里的 `switchRuntime`、`resumeSwitch` 没有在完整的 `createBridge` 里端到端测试。它们的判断已下沉到 `memory-vectors.switchTarget` 并有单元测试，HTTP 转发也有测试；但"启动 → 自动调用 prepare 运行动作"这一段只做了代码审读，没有用测试覆盖。
- 方案 3.4 的"总开关中途关闭：停止且不再自动续建"：停止沿用现有撤销逻辑（`revokeCloudBackends` 加 `cloudAllowed` 守卫）；新增的部分是"关闭后意图被清除"，已有测试。没有专门再写"准备进行到一半时关闭开关"的用例。
- 界面没有在真实浏览器或宿主里跑过，只有基于假 React 的渲染测试。
- 已知的小竞态：查询读完 profiles 状态后、登记引用计数前，如果恰好有一次 build 完成并清理了那份快照，这次查询会得到 `INVALID_PROFILE_SNAPSHOT`，在 portable 层降级为空向量结果（文字与条目照常）。窗口只有一个异步间隙，后果和现在"建索引期间降级"一样。

没有遇到方案第 5 节的停止条件：没有改 `sameDocument`、索引身份、表结构、`singleBackend`，也没有本方案之外的测试失败。
