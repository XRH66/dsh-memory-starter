- 融合后只调用一次重排。
- 预取使用 `prefetchRerankCandidates`，默认 `16`；工具检索继续使用 `memoryRerankCandidates`。

## B2 准入门槛与折叠

### 规则原文

本次实现严格对应任务单中的以下规则：

- 本次检索的重排已执行时，只看 `signals.rerank >= options.minRerank`。
- 更正原话是例外：`signals.rerank >= options.minRerank * 0.6` 即可准入。
- 不在重排前 K 条里的记录，`rerank` 为 `null`，不准入。
- 重排未执行时，满足任一条件即可准入：
  1. 词面强：`signals.lexical >= options.minLexical`，默认 `0.6`。
  2. 向量强：`signals.similarity >= minSimilarity + options.vectorMargin`，默认边距 `0.10`。
  3. 两路一致：同一记录在文字和向量两路都命中，且 `lexical >= 0.3`，且 `similarity >= minSimilarity`。
  4. 更正优先：`source.changeKind === 'correction'`，且 `lexical >= 0.3` 或 `similarity >= minSimilarity`。
- 一律不准入：`state.validity` 为 `historical` 或 `disputed`；正文为空。
- 已准入的当前有效条目若 `source_refs` 指向某条原话，就丢弃该原话；例外是该原话为更正且时间晚于条目。
- 两条记录正文规范化后，短文本被长文本包含，或汉字二元组 Jaccard 相似度 `>= 0.7` 时只保留一条。
- 保留优先级为当前条目、旧笔记、原话；同优先级保留排名靠前者。
- 最多 `options.maxRecords` 条，默认 `3`；同时受 `prefetchMaxChars` 约束，默认 `1000`；保持原排名顺序。
- `stats` 为 `{candidates, admitted, rejected, folded, injected, chars}`，并带 `{lexical, vector, agree, correction}` 计数。

### 实现说明

- `selectPrefetch({records, minSimilarity, options})` 返回 `{lines, stats}`。
- 重排状态由调用方以 `options.rerankApplied` 传入，值来自 `channels.rerank.state === 'applied'`。
- 规范化会做 NFKC、转小写，并去掉空白和标点。
- 输出行包含标签和正文；字符预算按行累计，不拆分代理对。

## 发现

- `package.json` 的 npm 运行时白名单不包含 `lib/memory-prefetch.js`，而 `package.json` 不在本任务允许修改的文件内。为保持 npm 包自包含，选择器实际实现放在已打包的 `memory-query.js`，`memory-prefetch.js` 公开转出 `selectPrefetch` 和 `shouldPrefetch`。这与 A 批处理 `shouldPrefetch` 的边界一致。
- `scripts/bench-prefetch.mjs` 不在允许修改清单内，且当前脚本只测检索会话，不经过 `selectPrefetch` 或 `prefetchMessage`。因此无法按任务单要求在“测速脚本里”得到改前改后的最终平均注入字数和 token；本回执只报告可核验的测速、上限和脚本限制，没有把检索结果长度冒充最终注入平均值。
- 任务单要求的原因计数只有 `lexical`、`vector`、`agree`、`correction` 四项，没有单独的 `rerank` 原因计数。重排准入仍可通过 `admitted`、`injected` 和候选计数观测；若后续需要区分重排直接准入数量，应另行扩展统计契约。
- 本次没有发现需要越出任务单文件边界顺手修改的其他源码问题。
