## 改动一：检索结果瘦身

### 问题

`memory_search` 在 token 模式下（`createMemorySearchSession` 传了 `tokenLimits`），每条结果都把 `id`、`revision`、`anchor`（含重复的 id、revision、ref、range）、`sourceIds`、`source`、`time`、`localTime`、`kind`、`role` 等字段原样序列化给模型。实测一条 14 token 的原话，序列化后有 154 token。单次检索预算 1024 token，于是只装得下 2–3 条，r5 里 182 次检索有 179 次撞到预算，后来的更正常被截掉。

### 目标

模型看到的每条结果只保留读懂它需要的东西。完整定位信息留在服务端，用短编号对应。同样 1024 token 下，短原话应能返回 8 条以上。

### 设计

1. **只改 token 模式**。非 token 模式（不传 `tokenLimits` 的旧 Suzu 合约）的行为、字段和测试保持不变。

2. **模型视图字段**（token 模式下 `fit()` 产出、计入预算、返回给调用方的每条记录），只允许以下字段：
   - `ref`：本次回答内的短编号，形如 `"m1"`、`"m2"`……，在同一个 search session 内按发出顺序递增，不复用。
   - `label`：沿用后端给的 `label`（已含类型、说话人、本地时间、相对日、条目的有效性和进展）。
   - `text`：正文（被预算截断时照旧截断）。
   - `truncated: true`：仅在截断时出现。
   - `correction: true`：仅当后端记录的 `source.changeKind === 'correction'` 时出现（对应 `lib/memory-query.js` 里 `newestCorrection` 置顶的那条）。
   - 记忆条目可保留 `subject_ref`、`tags`，前提是它们非空。其余字段（`id`、`revision`、`anchor`、`sourceIds`、`source`、`time`、`localTime`、`kind`、`role`、`type`、`state`、`importance`、`evidence_basis`、`speaker_ref`、`viewpoint_holder_ref`、`inferred_by_ref`、`source_refs`、`sourceStatus`）不再给模型。它们的信息已经在 `label` 里，或者只有服务端需要。

3. **服务端映射**：`search-session.js` 现有的 `anchors` Map 改为以 `ref` 为键，值为冻结的 `{ id, revision, anchor }`（anchor 为截断后实际交付范围对应的 anchor，和现在写入 `anchors` 的内容一致）。`seen`、`expanded` 仍按 `keyOf(record)`（id + revision）去重，不变。

4. **`memory_open`（expand）**：token 模式下输入改为 `{ ref: "m3" }`（字符串），用 Map 换回完整 anchor，后续逻辑不变。找不到 ref 返回 `INPUT` 错误。展开结果里的每条记录同样转成模型视图并发新 `ref`。续页时，`anchor.nextOffset` 存在服务端映射里，模型拿新 `ref` 再次 open 即可续读。
   - `lib/memory-query.js` 里 `memory_open` 的参数定义从 `{anchor:{type:'object',required:true}}` 改为 `{ref:{type:'string',required:true}}`，描述里所有「anchor」的说法改成「ref（结果里的短编号）」，并保留「不得编造 ref」。
   - `memory_search` 的描述里「用 memory_open 展开相关 anchor」改成「用 memory_open 展开相关 ref」。「source.changeKind=correction」改成「标有 correction 的记录」。
   - `memory_recent` 的结果同样走模型视图。

5. **给服务端用的查询方法**：search session 增加 `resolve(ref)`，返回 `{ id, revision, anchor }` 或 `null`，只供本进程代码和测试使用，不出现在工具输出里。现有测试凡是从结果里读 `.anchor`、`.id`、`.revision` 来断言偏移、版本的，改成 `session.resolve(record.ref)` 后再断言同样的内容，**断言的含义不能放宽**。

6. **条数上限**：`lib/memory-contract.js` 的 `MEMORY_QUERY_DEFAULTS.records` 从 5 改为 10。`searchTokens`、`openTokens`、`totalTokens`、`calls`、`waitMs` 不变。`memory-query.js` 里 `limit` 参数描述中的「最多返回5条」改为「最多返回10条」。

7. **预检索**：`lib/index.js` 的 `prefetchMessage` 只用 `record.label` 和 `record.text`，不需要改。确认它在新格式下仍然工作即可，并在回执里写明。

8. **外层元数据**：`budget`、`channels`、`timings`、`coverage`、`nextPage` 等外层字段的现有行为不变，本次不压缩它们。

### 新增测试（写进 `test/memory-query.test.js` 或 `test/memory-query-session.test.js`）

- 存入 12 条虚构的短原话（每条约 20 个汉字，彼此相关），用默认 token 预算检索一次。断言：
  - 返回条数 ≥ 8；
  - 每条记录的键只在第 2 点允许的集合里；
  - 序列化结果里不出现 `"anchor"`、`"revision"`、`"sourceIds"`。
- 用检索返回的 `ref` 调用 open，能展开到同一条原文；对一条长文本连续 open 续页，偏移正确（用 `resolve` 核对）。
- 用不存在的 `ref`（如 `"m999"`）open，返回 `INPUT`。
- 一条带 `changeKind: 'correction'` 的记录在模型视图里有 `correction: true`。
- 非 token 模式（不传 `tokenLimits`）下记录格式与改动前完全一致（可复用现有测试）。

## 改动二：回答规则改写

### 问题

155 道错题里有 128 道必答项全对，却因为补了记录里没有的细节被判错：给过去补时段、日期、年龄；给现在补天气和状态；替第三方编台词；顺带说出第三方的私事。现有规则开头是「回答涉及用户过去说过的事时」，模型把这些当成了正常的聊天润色。

### 改法

1. `lib/memory-query.js` 的 `ANSWER_RULES` 整体替换为下面 7 条（逐字照抄，不要加题目里的例子）：

```js
export const ANSWER_RULES=[
  '只把记录（近期接续、记忆检索结果）里实际写到的内容当成事实说',
  '不要自己补记录里没有的具体时刻或时段、日期、数字、地点、天气、人物现在的状态、别人的反应或原话、事情的后续进展和原因；记录里没有就不说，或直接说没有记录',
  '计划、打算、约定在没有后续确认前，不能说成已经发生',
  '时间只用记录给出的时间和程序标注的相对日（今天、昨天、N 天前）；说到现在几点几号，照给出的当前本地时间原样说，不取整、不估算',
  '同一件事前后说法不同时，以时间最新的说法为准，并点明之前的说法；记录没说明原因就说原因不明，不要替它找原因',
  '只回答被问到的事，不顺带提无关的旧事，不主动说第三方的健康、婚姻、家庭、经济等私事',
  '给建议、做推测或按用户要求续编时可以发挥，但要说明这是建议、推测或新编的内容，不能和记录里的事混在一起说成已经发生',
];
```

2. `lib/index.js` 的 `makeAnswerGuidanceMessage` 里，`'回答涉及用户过去说过的事时：'` 改为 `'本轮整个回答（包括闲聊、建议和续写）都要遵守：'`。其他行不动。

3. `memory_search` 描述里拼接 `ANSWER_RULES` 的方式不变（它会自动用上新规则）。

### 测试

- 新增一条：回答规则消息包含新标题行和全部 7 条规则，且仍带「这些规则不是用户记忆，不得保存为事实」。
- 现有测试若断言了旧规则原文，改为断言新原文，并在回执里列出。
