# 记忆继承标准（草稿，2026-11-14）

精简计划第 3 步，取代 `lib/legacy-import.js` 的"调用整理模型分 12 类"迁移。

**范围：只管本项目旧版本的记忆转成新版本的格式。**用户升级后，旧版留下的笔记和条目由程序直接转过来，不调用模型。其他软件的导出（别的聊天软件、日记应用等）不在本标准范围内。

原则是：**旧记忆只搬，不分类、不改写**。搬进来以后和原话放在同一个库里，能搜到、能预取，在可视化页面上按时间线显示。下面的交换格式是转换的中间结果，用来检查和核对，用户不需要自己写。

## 一、交换格式

文件用 UTF-8 的 JSON Lines，扩展名 `.jsonl`，每行一个 JSON 对象。

**第一行是文件头：**

```json
{"standard":"dsh-memory-inherit","version":1,"source":"从旧版 Vault 导出","created":"2026-11-15T10:00:00+08:00"}
```

**之后每行一条记录：**

```json
{"id":"chats/facts/xxx.md","time":"2026-10-25","speaker":"summary","kind":"note","text":"……原文……","source":{"system":"basic-memory-0.3","file":"chats/facts/xxx.md"}}
```

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `text` | 是 | 正文，**原样照搬**，不改写、不摘要、不合并。最长 20000 字；更长的由转换方按段落切开，各自成条，并用 `part` 标号 |
| `speaker` | 是 | 谁写的：`user`（用户）、`assistant`（助手）、`summary`（整理摘要，即旧笔记、旧条目这种别人归纳过的东西） |
| `kind` | 是 | 种类：`message`（对话原话）、`note`（笔记）、`diary`（日记） |
| `time` | 否 | **写下或说出这句话的时间**，不是事情发生的时间。可以是带时区的完整时间，也可以只到日期。不知道就省略，**不要猜** |
| `source` | 是 | 来源：`system`（来自哪个系统或软件，自由填写）、`file`（文件名或相对路径），可选 `locator`（行号、链接等） |
| `id` | 否 | 来源里的稳定编号。有就填，重复导入时靠它判断是不是同一条 |
| `conversation` | 否 | 原话所属的对话编号。同一编号的原话会按 `order` 排成上下文 |
| `order` | 否 | 在对话中的顺序（整数） |
| `part` | 否 | 长文切开后的序号，从 1 开始 |
| `tags` | 否 | 自由标签（字符串数组）。只用于显示和筛选，不参与分类 |

**硬性约定：**

- 正文里提到的日期、人名、数字原样保留。程序和转换方都不去推断"这件事发生在哪天"。
- 不需要、也不接受"类型 / 主体 / 属性 / 有效性"这类分类字段。多出来的未知字段导入时忽略，并在检查结果里列出。
- 人设自己的主观笔记（`dafeiyu/` 下的日记、想法、图库）**不走这个标准**，照旧单独保存和显示。主题页（`index/`）是程序生成的，也不导入。

## 二、导入后怎么存、怎么用

- **存放：**存进原话库，与对话原话同库，带上导入批次号、来源和种类。之后的向量编码、删除原话、"别再提"降权，都和普通原话走同一条路。
- **搜索标注：**
  - 对话原话照旧标"原话 · 用户说 · 时间"，末尾加"· 导入"；
  - 整理摘要标"旧笔记（整理摘要） · 写于 时间"，让模型知道这是当时归纳的，不是原话。
- **权重：**整理摘要在排序时打折，默认乘 0.7。和原话说法冲突时，按回答规则"以最新的为准，并点明之前的说法"处理，程序不做去重或判断。
- **不调用模型：**导入本身一律不调用模型。向量编码照常在后台做；用云端向量时会产生一点编码费用，检查结果里要预估。

## 三、导入工具的把关

1. **先检查、后导入。**检查只读不写，给出：
   - 条数，以及各种类、各说话人的数量；
   - 时间范围、没有时间的条数；
   - 逐行错误：第几行、哪个字段、错在哪、怎么改；
   - 预计向量编码量。

   有任何错误就整份不导入。
2. **重复导入不产生重复记录。**同一来源、同一 `id`（没有 `id` 时用"来源 + 时间 + 说话人 + 正文"的哈希）、正文相同的，跳过；同号但正文不同的列为冲突，不导入，也不覆盖。
3. **整批撤销。**每次导入有一个批次号，可以在维护页按批次整批撤销。撤销走"删除原话"的同一机制，可以恢复。
4. **原文件只读。**工具只读文件，不改、不移动、不删除。
5. **规模上限：**单个文件不超过 50MB，不超过 10 万条。

## 四、内置转换（程序直接转，不用模型）

| 来源 | 转法 |
| --- | --- |
| 0.3.0 及更早的旧笔记（Vault 的 `chats/facts`、`events`、`history`、`review`，带 `memory_id` 文件头） | 正文取 `value`，没有就取正文部分；时间取 `recorded_at`，没有再取 `created`；说话人 `summary`，种类 `note`；`id` 用相对路径；文件头里的主体、属性等放进 `tags`，只作显示用 |
| 0.4～0.6 的整理条目（Vault 条目目录） | 正文取条目正文；时间取它依据的原话时间；说话人 `summary`，种类 `note`；`id` 用条目编号。**暂缓**：条目是从原话整理出来的，原话本身已在库里；用户的日常库条目为 0 条。以后有需要再做 |
| DSH 聊天记录 | 沿用现有的 `raw-rag/history.js` 导入（已经是原话，已有幂等），不经过本格式 |

## 五、用户怎么继承

第一批（任务单20261115-I）先做命令行入口 `scripts/inherit-memory.mjs`。维护页那一栏和"对 DSH 说一句"等设置页重做时（可视化页面那一步）再接上，两者都调用同一个导入模块。

- **维护页"继承旧记忆"**：程序自动找到旧版的 Vault 目录（也可以手选），转换后先给检查结果，用户确认后才导入。
- **对 DSH 说一句就行**：用户对自己的 DSH 说"把旧记忆搬过来"，DSH 通过管理入口发起同样的转换和检查，把检查结果念给用户，用户确认后才导入。导入属于管理操作，需要用户在当前对话里明确同意。
- **转不了的文件**：比如手工改坏了文件头的笔记，在检查结果里逐个列出原因，跳过不导入，其余照常导入。用户可以修好文件再导一次，已经导入过的会自动跳过。

## 六、用户自己的库怎么核对（第 3 步验收）

1. 先用内置转换做检查：应得 70 条，种类全是 `note`、说话人全是 `summary`，时间范围约 10-24～10-30（以实际为准）。
2. 导入后逐条自动核对：用每条正文开头 20 个字做全文搜索，都能搜回自己。
3. 对比旧笔记通道：同一组查询，导入前走旧笔记通道的结果，导入后都要能从原话库这一路搜到。
4. 核对通过后，才能做第 4 步：去掉旧笔记通道和 `legacy-import.js`。
