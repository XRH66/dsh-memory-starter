## 执行器结构

### 入口与隔离

- `bench-normal.mjs` 为每个人物创建独立运行目录、独立 DSH Home、独立记忆库和独立历史种子会话。
- 每次启动使用随机 `127.0.0.1` 端口；没有连接、重启或修改日常 3080。
- 人物并行上限 `2`；本次只跑 P01，实际人物并行 `1`。
- 考试并发上限 `4`；同一人物实际观测到的最大并发为 `4`。
- 日常模型凭据只经 `dailyRoute` 进入子进程环境；没有打开、打印或复制凭据内容。

### 历史、cutoff 与 settle

- 只回放到所选题目最后一个 cutoff。P01 全量为 `352` 轮，历史文件虽然还有 353 至 388 轮，但没有进入本次隔离记忆。
- 同一人物严格按轮次推进，历史轮次未完成前不进入下一轮。
- 每个唯一 cutoff 执行一次 settle。P01 全量共 `43` 个唯一 cutoff，对应 `43` 次 settle。
- settle 沿用原有的流水线和向量追平判定，没有缩短十分钟上限。
- 同一 cutoff 的题目共享同一冻结记忆状态，最多四题并发。

### 只读考试

- 每题创建独立考试会话。
- 调用顺序固定为：创建会话、选择作答模型、开启记忆、`setReadOnly(sessionId, true)`、核对状态、发送首条消息。
- 88 题全部通过首消息前的状态核对：记忆已开启，只读为真。
- 不调用撤回；关闭进程后从原话库和队列状态做独立写入核查。

### 时间与短期读取

- `clock.mjs` 增加 `AsyncLocalStorage` 任务级时间覆盖。
- 同一 cutoff 并发数题时，每题自己的检索、时间上下文、相对日期和衰减判断都使用该题 `now`。
- 88 题都有时间上下文记录，`parsedMs` 与题目 `now` 不匹配数为 `0`。
- 预取按宿主事件落盘；P01 全量有 `35` 个考试会话实际注入预取。

### 断点续跑

- 每题成功后把完整行追加到 `answers.jsonl`，`runStatus=ok` 的题在续跑时跳过。
- 人物已有 `plan.json` 和进度时，保留原隔离记忆和向量档案，只从 `progress.nextTurn` 继续；历史续接使用新会话，避免把超时回合重复追加到旧会话。
- 如果没有可恢复的计划或进度，才从该人物开头重放。
- 本次全量在第 352 轮历史等待 `turn/end` 达 120 秒后超时。核查显示原话库最新完整轮次为 351，87 题结果完整，因此使用上述“保留记忆、只补第 352 轮”的恢复路径。

### 结果与判分

- 每题记录回答、耗时、模型步数、工具调用、检索通道、预取、时间上下文、token、模型标识、只读状态和写入核查。

## 发现

1. 真实宿主下没有观察到短期首轮接续。新执行器四次真实运行的请求记录中 `handoffChars` 均为 0，P01 全量逐题 `handoffInjected=0`；预取则正常出现。`test/session-read-only.test.js` 表明只读首轮接续在单元夹具中可用，因此真实宿主路径仍有未解释差异，可能影响分数。按任务边界未修改仓库 `lib/`。
2. P01 最后一次历史轮次在第 352 轮首次回放时等待 `turn/end` 超时。核查后确认原话库只到第 351 轮，随后以新续接会话补写第 352 轮，未删除或撤回任何历史。
3. DSH 启动后会重写隔离 profile 的 `cordis.patch.yml`。续跑配置读取已改为 JSON 优先、YAML 兼容，否则第二次启动无法恢复模型代理地址。
4. 首次续跑再次触发向量 `prepare`，得到已有档案的 `PROFILE_BUSY`。最终策略是续跑已有活动档案时直接复用，只有档案缺失才重新准备。
5. 请求记录中观察到 7 次 `ECONNRESET`，对应请求仍拿到 HTTP 200 响应，最终 88 题都有非空回答；没有把这些记录成题目失败。
6. 发布校验的失败是现有白名单缺口，不是本批新增文件：`test/session-read-only.test.js` 已跟踪但未列入 `release-files.json`。本任务明确限定只改 `.local/benchmark-cmb/`、运行结果和本回执，因此没有修改 `release-files.json`。
