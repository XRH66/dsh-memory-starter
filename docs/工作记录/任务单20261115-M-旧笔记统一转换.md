# 任务单 M：旧笔记统一转换（0.3～0.6 一条路导入原话库）（2026-11-15）

## 背景

- L 批之后，搜索不再直接读 Vault 里的旧笔记，旧笔记只有导入原话库才搜得到。导入工具是 `scripts/inherit-memory.mjs`（实现在 `lib/inherit/`），现在只认 0.3 的笔记：`chats/facts|events|history|review` 下带 `memory_id` 的文件。
- 0.4～0.6 的长期条目也在 Vault 里，现在的导入工具一条都不认。Z 批之后程序也不再读它们，升级用户会悄悄丢掉这部分记忆。这些条目的格式以 `v0.6.0` 标签为准，用 `git show v0.6.0:<文件>` 查看：
  - **条目笔记**：在 `chats/entries/` 下（`lib/memory-entry-service.js` 第 41 行，由 `captureFolder` 加 `/entries` 得到）。文件头有 `memory_entry_id`、`memory_entry_schema: memory-entry-v1`、`memory_type`、`state_validity`、`state_progress`、`memory_source_refs`（JSON 字符串）、`evidence_basis`、`legacy_import_from`（JSON 字符串，0.5 起"旧记忆迁移"从 0.3 笔记转来的才有）、`occurred_at`、`recorded_at`/`created`、`tags`。写法见 `lib/memory-entry.js` 的 `memoryEntryMetadata`，文件头的序列化见 `lib/vault-files.js` 的 `renderNote`。
  - **条目正文**：夹在 `<!-- dsh-memory-entry:start -->` 和 `<!-- dsh-memory-entry:end -->` 之间（`lib/memory-entry-service.js` 第 12～17 行）。标记外面可能有标题行、主题链接行（`lib/entry-links.js` 的 `TOPIC_LINE_PREFIX`），也可能有用户自己补的文字。
  - **主题页**：在 `chats/topics/` 下，程序生成的内容固定是 `# 名称` 加一行"本页由记忆框架自动维护，可在下方自由补充"（`lib/entry-links.js` 的 `topicPageContent`），文件头 `tags` 含主题页标签。
  - **条目旧版存档**：条目被改写时，旧版本存成 `chats/history/历史 <uuid>.md`，文件头带条目字段、`state_validity: historical`，没有 `memory_id`（`lib/memory-entry-service.js` 第 188 行附近，`lib/memory-entry.js` 的 `historicalMemoryEntryMetadata`）。
  - **待确认的整理结果**：只在数据库的 `structured_entry_operations` 表里，没写进 Vault。
  - 数据库里的 `structured_entries` 表只是 Vault 条目笔记的副本，不作为导入来源。
- 公开升级说明 `docs/install/upgrade.md` 已经过时：还在教用户点"维护 → 旧记忆迁移"（Z 批已删），还写着"旧笔记按原样读取和检索"（L 批已删）。

## 目标

用户从 0.3、0.4、0.5、0.6 任何一个版本升级，都只走一条路：`check` 看清会导入什么、跳过什么，再 `apply`。同一条记忆不重复导入。说明文档只有一套。

## 一、转换规则（`lib/inherit/vault.js`）

一次扫描同时处理下面几类，结果合成一个记录列表：

1. **0.3 笔记**：规则、记录 ID（Vault 相对路径）和 `source.system`（`basic-memory-0.3`）都保持现状不变。日常库已经按这个格式导入过 70 篇，重跑必须全部判为"已导入"。
2. **条目笔记**（`chats/entries/` 下 `memory_entry_schema` 为 `memory-entry-v1` 的文件）：
   - 正文取标记之间的文字。标记外面用户自己补的文字接在后面，空一行；标题行和主题链接行不算。标记缺失或有多对时，跳过并写明原因。
   - 记录格式：`speaker: summary`，`kind: note`。记录 ID 用 Vault 相对路径，`source.system` 用 `basic-memory-0.6`（0.4～0.6 共用一个值），`source.file` 用相对路径。
   - 时间：先取 `recorded_at`，没有就取 `created`，和 0.3 一样。`occurred_at` 不当时间用，作为标签保留。
   - 标签：沿用 0.3 的 `key:value` 写法，带上 `memory_type`、`state_validity`、`state_progress`（有值时）、`evidence_basis`（有值时）和原有 `tags`。
   - 超长正文按现有 `splitInheritText` 切片。
3. **哪些条目导入、哪些跳过**：
   - 从 0.3 笔记迁来的条目（有 `legacy_import_from`）：导入。如果同一次扫描里 `legacy_import_from.path` 指向的 0.3 笔记也在，只导入条目、不导入那篇 0.3 笔记，因为条目是更新后的版本。被替代的 0.3 笔记计入跳过，原因写"已由新版条目接替"。
   - 没有原话来源的条目（`memory_source_refs` 为空，或 `evidence_basis` 为 `manual`）：导入。
   - 从对话整理出来的条目（`memory_source_refs` 不为空，且不属于上面两种）：默认跳过，原因写"由对话整理而来，原话已在原话库"。这些条目的依据就是原话库里的原话，再导入一份摘要只会重复，还可能带进整理时的推断。加 `--include-derived` 时照常导入。
   - `state_validity` 是任何取值都照常导入（`historical`、`disputed` 等写进标签），不改正文。
4. **主题页**（`chats/topics/`）：内容和程序生成的固定内容一致的跳过，不计为错误。用户在下面补了文字的，把补的部分作为一条记录导入（`source.system` 同条目，标签 `topic:<名称>`）。
5. **条目旧版存档**（`chats/history/` 下带条目字段、没有 `memory_id` 的文件）：跳过，原因写"条目旧版本存档"。0.3 的 `chats/history` 笔记（带 `memory_id`）照旧导入。
6. 其他目录不扫描。`dafeiyu/` 下的人设笔记由向量文档负责，不在这里导入。

转换只读文件，不碰数据库。`check` 的输出按类别给出计数：0.3 笔记、条目（导入 / 跳过及原因）、主题页、旧版存档、被条目接替的 0.3 笔记，再加上现有的导入预估（新增 / 已导入 / 冲突 / 已撤销）。

## 二、命令行（`lib/inherit/cli.js`）

- `check`/`apply` 不给 `--vault` 也不给 `--file` 时，默认用部署配置里当前记忆库的 Vault（`ownerDirectory/vault`，`deploymentConfig` 已经算出来了）。仍然只能二选一，两个都给时报错。
- 新增 `--include-derived`，只对 `--vault` 有效。
- `apply` 完成后的输出加一句提示：运行中的 DSH 要到「状态」页点「准备索引」（或重启），新导入的内容才会进向量索引；全文检索不需要。
- 帮助文字同步更新。`list`、`undo`、`restore` 不变。
