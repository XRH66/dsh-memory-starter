## 一、平时改代码：单元测试

- 全量：`node --test --test-timeout=60000 test/*.test.js`，**不要加 `--test-force-exit`**。约 20 秒。
- 每次改动后的收尾：
  1. 全量测试通过；
  2. `node .local/automation/check-tracked-privacy.mjs --worktree` 违规 0；
  3. 发布导出 `node .local/automation/export-release.cjs . <临时目录>` 的 `missing`、`broken` 为空；
  4. 新增的公开文件加进 `release-files.json` 和 `package.json` 的 `files`。
- 偶发失败：单独跑那个文件 3–5 次。单跑稳定、全量偶发失败的，多半是测试本身先清理后关闭的顺序问题，不要靠加长超时糊过去。
- 测试数据只用 `test/helpers.js` 的 `scratchDirectory` 和虚构内容。
- 改了哪块该看哪些测试文件，见文末附录。

## 二、双版本发版前实测（每次发版前都做）

同一天分别启动 DSH `0.2.1-rc.5` 和 `0.2.2-rc.3` 的隔离实例，两边都按同一套真实对话路径检查。不要碰日常 3080、`.local/runtime/`、`restart-dsh.ps1` 或真实记忆库。

### rc.5（端口 8933，模型代理 8934）

1. 用 `.local/automation/clean021-prepare.ps1` 从当前工作区打包并安装到私有 DSH 0.2.1-rc.5；确认生成新的 `clean021-root.txt`，不覆盖 `clean070-root.txt`。
2. 用 `.local/automation/clean021-start.ps1` 启动。脚本会调用 `clean022-model.mjs ensure <根目录> 8934` 自动写对话模型配置，并把 CC Switch 中 Github 账户的密钥只放进启动进程环境；代理用 `clean022-model-proxy.mjs <根目录> 8934`，默认 8932 行为不变。
3. 关记忆新建对话，确认模型请求里没有 `memory_*` 和 Basic Memory 工具。
4. 开记忆后确认工具出现；用户和助手原话都进入临时原话库；新对话问到该事实、能正确回答。
5. 关记忆后再发一轮，确认相关工具立刻消失。
6. 在开启记忆的对话中调用一次 `subagent` 做小事，确认子代理按同一对话识别（rc.5 的 `isOwnedBy` 路径），宿主和插件日志无相关报错。
7. 记录模型代理日志里的工具名和 token 用量，费用不超过 0.3 元；完成后停掉 8933 与 8934，保留隔离目录。

### rc.3（端口 8931，模型代理 8932）

1. 用 `.local/automation/clean022-prepare.ps1 -Commit <待测提交>` 准备私有 DSH 0.2.2-rc.3；用 `.local/automation/clean022-start.ps1` 启动。不得覆盖或删除 rc.3 实例的 `clean070-root.txt`。
2. 模型默认由 `clean022-model.mjs ensure <根目录>` 自动配置，密钥只进入进程环境；代理默认监听 8932。
3. 重复 rc.5 第 3～5 项：关记忆看不到记忆工具，开记忆后出现、双方原话入库、新对话能答对，关掉后工具消失。
4. 在开启记忆的对话中调用一次 `subagent`，确认 rc.3 的 `currentInitiator()` 兼容路径仍能识别同一对话，日志无相关报错。
5. 记录工具名、token 用量和费用；完成后停掉 8931 与 8932，保留隔离目录。

每轮实测都要核对：上述脚本实际启动的端口、DSH 版本和插件版本；模型代理记录的实际工具名；临时原话库只读统计和指定虚构内容；相关日志中 `basic-memory`、`session-memory`、`Trusted agents and sessions services required` 的报错数。登录地址和令牌只留在宿主日志，不复制到终端输出或回执。

## 三、全流程测试（发版前做一次；改了安装、首次配置、依赖时也做）

**一个 Codex 会话，从头到尾串行跑**，约 1 小时，真实模型调用很少。所有结果写进同一份回执 `docs/工作记录/回执<日期>-全流程测试.md`，每段一节。哪段失败就停在哪段，写清原文报错；修好后从这一段接着做，前面的段不用重来。

**通用规则**

- 只在系统临时目录下的 `dsh-full-<时间>` 里操作，隔离 DSH 用端口 8941，`DSH_HOME` 指向临时目录。
- 不碰日常 DSH（3080）和真实记忆库，只停自己启动的进程。
- 不输入、不复制、不打印任何密钥。带令牌的页面地址只打印到 `?` 之前，并告诉用户去哪个日志文件找完整地址。
- 接口操作：先 GET 带令牌的地址拿到 cookie，请求头带 `x-basic-memory-settings: 1`，路径是 `/api/basic-memory-settings/*`。
- 用到的接口：
  - `/sessions`：对话开关、检索服务、重排；
  - `/runtime`：向量档案、检索耗时和重排状态；
  - `/model-install`：下载模型。
- 0.7.0 起没有整理层：没有整理模型、条目、待确认和旧记忆迁移页面，也没有 `/legacy-import` 接口。

### 第 0 段：单元测试

先跑全量单元测试。不过就不往下做。

### 第 1 段：安装

1. 按本仓库对应版本标签（如 `v0.7.0`）的 README 和安装说明，**从 GitHub 安装**，在临时目录里生成独立部署。这一步同时验证合并后的安装器。
2. 在 8941 端口启动。
3. 记录 DSH 版本，以及两个插件实际装上的版本和提交（从档案里的 `package.json` 读）。
4. 和安装说明不一致的地方，逐条记进回执。

### 第 2 段：首次配置（唯一需要用户动手的一段）

停下，在终端里清楚告诉用户，请他在隔离页面里一次配好下面这些：

1. 对话用的模型服务（和日常相同）；
2. 「记忆框架」首次配置：填临时目录下的**新**记忆目录、勾一个对话、点启用（不再选整理模型）；
3. 一个**向量接口服务**（如硅基流动 `BAAI/bge-m3`），先保存，不切换（第 4 段要用）；
4. **重排服务**（如硅基流动 `BAAI/bge-reranker-v2-m3`），先保存，**不打开**重排。

用户说「已配置」后，按页面提示重启，再继续。

### 第 3 段：对话、检索、接续

1. 对话 A 开启记忆，发 3–4 条**自然日常对话**。不要用“记一下”“请记住”这类指令，否则只测到显式记忆意图，测不到真实生活聊天。例如：
   - 「团子今天又把我的水杯推到桌边了。三岁的橘猫还是这么手欠，不过看它装没事又舍不得说它。」
   - 「周六上午十点植物园门口见，我到时候带两瓶水。」
   - 「刚点了杯冰美式，还是不加糖喝着舒服，太甜的真喝不惯。」
   - 「昨天下午去海边走了走，顺手捡了块灰色的小石头，准备放书桌上。」
2. 新建对话 B 并开启记忆：
   - 开头是否带进了 A 的短期接续；
   - 问「我的猫叫什么？」，回答前是否调用了 `memory_search`，答案是否正确。
3. 新建对话 C，**不开启**记忆，发一句话，确认这句没有进原话库。
4. 只读打开隔离库：
   - A 的原话是否已入库，且不含思考和工具调用；
   - 状态页向量队列追平后，原话的向量是否都已建好；
   - 对话 B 的回答里，预取材料的标注（说话人、日期、相对日）是否正确。

### 第 4 段：向量与重排

1. 打开「原话检索」。在「检索模型」页下载 **BGE-small-zh-v1.5**，核对文件校验通过，保存启用，按提示重启，点「准备索引」等就绪。
2. 再问一次「我的猫叫什么？」，看向量通道是否有结果。
3. **打开重排**（用第 2 段保存的服务），问同一个问题。确认：
   - 检索结果标明已重排，顺序和不开重排时有变化（两次结果都记进回执）；
   - 状态页能看到重排耗时。
4. **重排失败退回**：把重排的超时临时调到最小（或换成连不上的地址），再问一次。确认结果照常返回、退回原来的排序，对话不报错、不卡住。之后把重排设置恢复原样。
5. **档案切换**：
   - 切到第 2 段保存的接口服务，建索引；
   - 再切回 BGE-small，确认复用原档案、只补差量，文档数没有从零开始；
   - 「检索模型」页的档案表信息正确：维数、文档数、未建索引的标「未建索引」。

### 第 5 段：删除原话

1. 「维护 → 删除原话」搜「团子」，确认后删除。
2. 再检索：原话通道和向量通道都不再返回这条，预取和 `memory_open` 也拿不到。

### 第 6 段：旧库切换与继承旧笔记

1. 在临时目录按 0.3.0 布局造一个虚构旧库：
   - `data/vault/chats/` 的 `facts`、`events`、`history` 下放约 15 篇带 `memory_id` 文件头的旧笔记，格式照 `test/inherit-vault.test.js` 的虚构笔记；有的带 `recorded_at`，有的只有 `created`，有一篇两者都没有；
   - 另放 2 篇转不了的：文件头坏了、正文为空；
   - 再建一个 `data/management`。
2. 记下所有旧笔记文件的哈希和修改时间。
3. 「维护 → 记忆库」切到这个旧库，重启。确认当前记忆库已切换。
4. 用 `scripts/inherit-memory.mjs`（`--deployment` 指向隔离部署）依次做：
   - `check --vault <旧库 vault>`：报告条数、时间范围、没有时间的条数、2 篇坏文件及原因、预计向量编码条数；
   - `apply`：记下批次号和新增、跳过、冲突条数；不重启 DSH，直接在对话里问一件旧笔记里的事，确认能搜到，标注是"旧笔记（整理摘要） · 写于 …"，没有时间的那篇标"写于时间不详"；
   - 再 `apply` 一次：全部跳过，没有重复；
   - `undo --batch <批次号>`：再问，搜不到；`restore --batch <批次号>`：又能搜到；
   - `list`：批次信息正确。
5. 核对：**旧文件哈希和修改时间全部不变**；导入的记录不出现在短期接续里；状态页向量条数增加的数目和导入条数对得上。

### 第 7 段：收尾

1. 停掉自己启动的隔离 DSH，确认 8941 端口已释放。
2. 临时目录保留不删，在回执里写出路径。
3. 回执最后列「通过 / 不通过 / 没做」三栏汇总。

**这次测试之外的事：**

- 日常里的旧笔记导入（70 篇）：新代码部署到日常 DSH 后、经用户同意再做，只核对条数、能否搜到和向量条数，不读笔记正文，不遍历读真实库。
- 0.4～0.6 结构化条目的继承转换暂缓（见[记忆继承标准](规范20261114-记忆继承标准.md)）。

## 四、日常增量与基准测试

### 日常增量性能（改写入、接续、检索或后台调度后做）

日常没有“先建库再聊天”的步骤。正常的开启记忆会话应当边聊边保存，前台先使用已写入的原文和接续，后台只做向量增量。

在隔离 DSH 的已有测试库或虚构库里按顺序发送自然消息，记录：

1. 开启记忆与不开启记忆时，单轮对话完成时间的中位数和高位值；
2. 每条正文写入后，多久能从原话检索和下一轮接续读到；
3. 每批消息后向量队列的数量，以及空闲时多久追平；
4. 检索超时、向量服务失败时，聊天是否在既有硬时限内退回且不暴露技术错误。

这组检查不要求回放整套基准历史，也不使用“全库建成耗时”作为日常延迟。模型切换后的首次准备索引、地址或维数变更后的重建、故障恢复另行记为维护成本。

### 基准测试（单独做，要用户提出）

- 用途：看回答质量有没有退步。要花钱，正式 714 题按正常执行口径目标不超过 2 小时，争取接近 1 小时。
- 题库固定第一版 `natural-timegrid-20261101-v2`（6 人物、714 题、461 个唯一 cutoff），不切 2.1／2.2。
- 正常执行方案：[方案20261113-基准执行器正常化](方案20261113-基准执行器正常化.md)。
- 现行重执行器的详细参数和压力验证边界：`.local/benchmark-cmb/全部用法.md`；其逐题完整 DSH 流程不等同正常正式成绩口径。
- 基准中的历史回放是冷启动，不是日常每轮聊天的建库步骤。
- 回执必须拆开记录：历史回放、向量追平、考试检索、考试回答、判分和重试退避。
- 现行做法（2026-11-15）：
  - 正常执行器 `bench-normal.mjs` 已做好并用了多次；默认关短期接续，4 题并发。
  - 每次较大的代码改动后跑一次 P01（约 40 分钟加判分、¥3–5），结果加进对照网页，和上一次对照看对错互换。
  - 发版前可加跑 P17，看另一个人物有没有退步；完整 714 题目前不跑。
  - 先免费演练：`--dataset demo --personas PUB01 --mode fake --turn-limit 40 --exam-limit 8`，演练最后判分会报"Unknown question"（判分包只认正式题库），属正常。
  - 驱动在 `.local/benchmark-cmb/lib/normal-driver.mjs`，已兼容没有整理流水线的代码。
- 只做通用改进，不针对基准题调。
