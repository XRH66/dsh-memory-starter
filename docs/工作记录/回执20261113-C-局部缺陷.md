# 回执 C：局部缺陷修复（2026-11-13）

## 结论

任务单 C1–C9 在修改前仍然存在，均已按任务边界修复。每项都补了回归测试，并在旧实现上先确认失败；没有提交、推送、打标签、重启 DSH、读取真实记忆库或调用付费接口。

改动只涉及任务允许的 `lib/client.js`、`lib/vault-files.js`、`lib/deployment-config.js`、`lib/legacy-import.js`、`lib/settings-host.js`、`lib/memory-entry-index.js`、`lib/raw-rag/install.js`、`lib/index.js`（仅 C9），以及对应现有测试文件。没有新增发布文件，因此未改 `release-files.json`。

## 逐项回执

### C1 前端 `setPlan` 作用域

- 问题仍然存在：`ModelPreparation` 的 `act` 会处理响应中的 `plan`，但 `setPlan` 定义在另一个组件作用域内。
- `/model-install` 返回 `plan` 的动作只有 POST 的 `action === 'plan'`。`inventory` 返回安装清单，`start` 返回 `job`，`cancel` 返回 `job`；当前 `ModelPreparation` 实际只发起 `start` 和 `cancel`。
- 修改方式：给 `ModelPreparation` 增加可选属性回调 `onPlan`，响应带 `plan` 时只调用 `onPlan?.(value.plan)`；未传回调时安全忽略，不再引用外部 `setPlan`。
- 新测试：`a model preparation plan response uses its own callback and never a sibling state setter`。
- 旧代码失败：是，回调未收到计划对象。

### C2 Vault 单文件格式错误隔离

- 问题仍然存在：`list()` 和 `search()` 遍历到单个不支持的前置元数据文件时会中断整个操作。
- 修改方式：两处逐文件捕获 `FRONTMATTER_ERROR`，跳过坏文件并通过 `logger?.warn` 记录文件相对路径，不记录正文；其他错误继续抛出。
- 新测试：`listing and search skip one malformed Vault file and log only its relative path`。
- 旧代码失败：是，`list()` 直接抛出 `MEMORY_FRONTMATTER_UNSUPPORTED`。测试同时验证普通读取错误 `EACCES` 仍会抛出。

### C3 向量档案切回比较维数

- 问题仍然存在：API 档案只比较地址和模型名，没有比较服务身份中的维数。
- 修改方式：复用 `ModelPicker` 内已有的 `dimOf` 换算规则，将服务维数与档案维数加入匹配条件；旧记录的 `0` 仍按 `1024` 处理。
- 新测试：`an API archive only reuses a saved service with the same endpoint, model and dimensions`。
- 旧代码失败：是，两个只有维数不同的档案都错误地显示了切换按钮。

### C4 配置锁

- 问题仍然存在：三个写入动作没有把 `EEXIST` 转成中文并发提示，且所有配置锁都没有陈旧锁恢复。
- 修改方式：新增统一的 `acquireLock(file)`，所有配置写入口改用它；锁文件写入 `{pid, at}`。遇到 `EEXIST` 时只检查并删除一次陈旧锁后重试：有效锁按 `at` 判断，超过 30 秒且进程不存在，或超过 10 分钟即恢复；内容无法解析或旧格式回退到文件修改时间，超过 30 秒即恢复；正常释放逻辑保持不变。
- 新测试：
  - `all deployment writers turn a recent lock into the same Chinese concurrency error`
  - `stale deployment locks recover for old unreadable, dead-owner and ten-minute cases`
- 旧代码失败：是，三个入口返回原始 `EEXIST`，陈旧锁也全部保持阻塞。

### C5 Windows 重命名重试

- 问题仍然存在：Vault 原子写入遇到 `EPERM`、`EACCES`、`EBUSY` 不重试，且失败清理没有对应回归覆盖。
- 修改方式：`atomicWrite` 按现有部署配置保存策略退避重试，最多 5 次；最终失败仍由原 `catch` 关闭句柄并删除临时文件。
- 新测试：
  - `atomic writes retry transient Windows rename contention and remove the temporary file`
  - `an exhausted atomic rename retry reports the error and leaves no temporary file`
- 旧代码失败：是，首次 `EPERM` 即失败，持久错误也只在第一次调用后退出。
- 没有提取新共享模块：新建模块需要同时进入运行时打包闭包，但任务文件白名单未包含 `package.json`。为避免留下“源码有、安装包无”的模块，保留了 Vault 内的局部重试循环。

### C6 旧记忆确认导入的并发

- 问题仍然存在：两个并发 `decide` 都能读到 `pending` 并进入条目写入器；同时存在无效的重复字段拷贝。
- 修改方式：选择 `committing` 状态方案。文件锁内原子地把 `pending` 抢占为 `committing`，只有抢占成功者执行导入；成功后原子改为 `committed`，失败退回 `pending`。启动时扫描残留 `committing`，按旧笔记的 `memoryId + checksum` 在条目服务中查找已写入目标，找到则补记为 `committed`，否则退回 `pending`。选择状态机而不是进程内互斥，是因为它同时满足并发去重和重启恢复。
- 同时移除了 `{...record.candidate, content: record.candidate.content}`，直接使用候选对象。
- 新测试：
  - `concurrent confirmation of one pending id only reaches the entry writer once`
  - `restart recovers committing records by checking the imported target and otherwise returning them to pending`
- 旧代码失败：是，并发测试调用条目写入器两次；重启测试把记录留在 `committing`。

### C7 设置接口输入校验

- 问题仍然存在：POST 分支分别解引用 `JSON.parse` 结果，非对象值会产生 `TypeError` 或落入错误的分支提示；结构化搜索没有复用 `list()` 的页大小规则。
- 修改方式：在统一 `body(req)` 中要求解析结果是普通对象，`null`、数组和原始值返回中文 `请求内容必须是对象`；把 1–100 的整数限制抽成 `entryPageLimit`，`search()` 和 `list()` 共用。
- 新测试：
  - `settings POST bodies reject non-object JSON before any branch dereferences them`
  - `structured search uses the same integer page limit contract as list`
- 旧代码失败：是，POST 返回 `Cannot read properties of null`；搜索对非法页大小不报错。

### C8 安装回执路径约束

- 问题仍然存在：库内安装回执中的可执行文件、模型和缓存路径可以指向 `runtime/embedding-install-v1` 之外。
- 修改方式：读取 `pinned-artifacts` 回执时检查 `rawRecallPython`、`rawRecallCacheDir`、`rawRecallBgeModelDir`、`rawRecallOnnx*`、`rawRecallGguf*`、`rawRecallLlama*Server`；路径必须是绝对路径，并通过 `path.relative` 确认位于当前记忆库的安装根目录内。Windows 比较前统一小写；不在范围内的回执跳过。`mode === 'user-supplied-files'` 不做此约束。
- 新测试：`pinned receipts outside the library install root are skipped while user-supplied paths remain allowed`。
- 旧代码失败：是，较新的越界固定回执被选中；修复后回退到库内有效回执，用户自选文件回执仍可使用。

### C9 接续连续延后告警

- 问题仍然存在：缺少受保护系统头导致接续延后时没有连续计数或告警。
- 修改方式：以真实 `Session` 对象为键保存在内存 `WeakMap` 中的会话级计数，避免把正文或计数落盘。连续第 3 次延后记录一次 `logger?.warn`，内容只含会话编号和 `consecutive=N`；成功投递、无需投递或其他非延后路径清空状态。
- 状态寿命说明：现有 `sessions` 逐轮状态会在 `turn/end` 删除，不能直接跨轮保存计数；`WeakMap` 随会话对象回收，不泄漏、不写状态文件，也不保留已结束回合的业务状态。
- 新测试：`three consecutive deferred handoffs warn once per session and reset after a successful delivery`。
- 旧代码失败：是，连续 3 次已报告 `deferred`，但告警数为 0。

## 发现

1. 模型安装器当前给 BGE/fastembed 生成的默认缓存路径仍可能位于 `<记忆库目录>/embedding-cache`，而 C8 按任务要求只信任 `<记忆库目录>/runtime/embedding-install-v1` 内的固定回执路径。读取侧已按要求隔离，但生成侧与读取侧的布局不一致可能让这类 BGE 回执在下一次启动时被跳过。修改生成布局会改变安装路径行为，超出本次“回执读取约束”范围，未顺手修改。
2. C4 的三个原始 `EEXIST` 缺口均已通过统一入口覆盖；`beginDeploymentConfiguration` 原有的英文并发错误也随公共函数统一为中文。
3. 未发现需要跨任务单修改的阻塞问题。
