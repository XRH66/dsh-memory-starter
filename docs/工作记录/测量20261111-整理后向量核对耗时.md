# 测量：整理后向量核对为什么慢（2026-11-11）

## 做法

- 把 r5 的 P14 记忆库（虚构数据，原话 811 条、条目 497 条，向量文档 1121 个）复制到临时目录，删掉旧向量后从零开始。
- 向量用日常的硅基流动 `BAAI/bge-m3`（custom-api）。只从日常配置里读取地址、模型名和密钥文件路径，没有打印密钥。
- 用单独的 Node 脚本直接组装插件（`createBridge`），不经过日常 DSH，也不碰真实数据。测完已删除临时库，`X:/Aiapp/basic-memory` 没有改动。
- 计时方法：包一层 `fs/promises` 的读写函数，统计调用次数和耗时，另外统计 `fetch` 的次数和耗时。

## 结果

| 场景 | 总耗时 | 读文件 | 写文件 | 接口请求 |
|---|---|---|---|---|
| 从零建索引 | 386 秒 | **137 万次，124 秒** | 1133 次，0.5 秒 | 1121 次，153 秒 |
| 增量核对，没有任何改动 | 20 秒 | **12.5 万次，11.6 秒** | 27 次 | 0 |
| 增量核对，改了 3 个条目文件（两轮） | 95 秒 / 95 秒 | **62.5 万次，59.6 秒** | 1153 次，0.4 秒 | 3 次，0.5 秒 |

真正需要重新算向量的只有 3 条，接口只花了 0.5 秒，其余 94 秒都耗在本地。

## 原因

`lib/vault-files.js` 的 `read()`（第 223 行）每次都调用 `resolveNote`：
- 先按「项目相对路径」直接读；记忆条目的标识是 permalink，和文件路径对不上，所以直接读失败；
- 然后退回到**把整个 Vault 的 Markdown 文件逐个读出、解析 frontmatter，比对 permalink**。

`lib/memory-documents.js` 的 `noteDocument` 其实已经把记录里存的文件路径作为 `knownFilePath` 传进来了，但 `read()` 完全没有用它。

所以每读一个条目，都要把整个 Vault 扫一遍。增量核对要逐条确认所有条目还有效，于是变成「条目数 × 文件数」：P14 约 500 个条目文件，一轮下来就是几十万次读取。条目越多，增长越快（平方级）。

之前怀疑过的另外两点，实测都不是主因：
- 每条写一次进度文件：一轮 1153 次，总共只要 0.4 秒；
- 每次核对都重建快照：没有单独计时，但除去读文件后剩下的时间不多。

## 对日常的影响

- 日常 Vault 现在只有 82 个 Markdown 文件，平方级的放大还不明显，单轮核对估计只要几秒。
- 不过每次整理都会新增条目，增长是平方级的：条目到几百个时，每次整理后后台就要跑一到几分钟，这段时间会占着 CPU 和磁盘，向量检索也可能挤不上。
- 测试框架里「考前等待」长达几分钟，就是因为这个。

## 另一个发现：建索引时接口一条一请求

从零建索引时，1121 个文档发了 1121 次请求：每个文档单独调用 `embed`，同一批次只装同一文档的分块，而这里的文档多数只有一个分块。按文档合批（例如每批 16 个文档）可以把请求次数降到约 70 次。这只影响首次建索引和换模型，不影响日常的增量核对。

## 修复方向

1. **主修**：`read()` 在 `context.knownFilePath` 存在时，先直接读这个文件，permalink 对得上就直接返回；对不上或文件不存在，再退回原来的整库扫描（保持正确性）。
2. **兜底**：整库扫描时，在同一次核对内缓存一份「permalink → 文件」的索引，避免同一轮里反复全扫。缓存只在本轮有效，下一轮重建，不会读到过期内容。
3. **可选**：建索引时跨文档合批调用接口。

## 修复后复测（同一套脚本、同一份 P14 副本、bge-m3）

修复见 [回执](回执20261111-条目读取走已知路径.md)：`read()` 先按已知文件路径读，permalink 对上就直接返回。

| 场景 | 修复前 | 修复后 | 读文件次数 |
|---|---|---|---|
| 从零建索引 | 386 秒 | 247 秒 | 137 万 → 6963 |
| 增量核对，没有改动 | 20 秒 | 8.7 秒 | 12.5 万 → 994 |
| 增量核对，改 3 条（两轮） | 95 秒 | 28.6 / 28.9 秒 | 62.5 万 → 3995 |

建索引剩下的时间主要在接口请求上（1121 次，160 秒），按文档合批可以继续缩短。增量核对剩下约 28 秒，已经不在读文件上（只剩 1.3 秒），可能在快照登记、逐条确认原话来源等 CPU 和数据库操作上，下一步可以用 CPU 采样再查。
