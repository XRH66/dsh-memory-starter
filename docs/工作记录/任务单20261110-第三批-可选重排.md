## 接口事实（通用兼容格式；硅基流动、Jina、本机 llama-server `--reranking` 都接受这个格式）

代码、文案、函数名都不要写死硅基流动：模块叫“重排服务”，服务地址与模型名来自配置。后续可能接本机 llama-server 的重排端点（`http://127.0.0.1:端口/v1`），所以 R1 的回环 HTTP 放行要保留。


- `POST {apiBase}/rerank`，`Authorization: Bearer <key>`，JSON body：`model`、`query`、`documents`（字符串数组）、可选 `top_n`、`return_documents`（我们传 `false`）。
- 返回：`{ id, results:[{index, relevance_score}], meta:{tokens:{input_tokens,output_tokens}, billed_units:{...}} }`，`results` 按相关度降序，`index` 指输入位置。
- 只有 Qwen3-Reranker 支持 `instruction`；本批**不发** `instruction`、`max_chunks_per_doc`、`overlap_tokens`。

## R1 重排请求模块（新文件 `lib/raw-rag/rerank-http.js`）

- `rerankServiceUrl(baseUrl)`：规则照 `lib/raw-rag/embedding-http.js` 的 `embeddingServiceUrl`（只许 HTTPS，或本机回环 HTTP；拒绝用户名/密码/query/hash），路径末尾补 `/rerank`；若 baseUrl 以 `/embeddings` 结尾，先去掉再补 `/rerank`。
- `requestRerank({baseUrl, model, query, documents, apiKey, signal, fetchImpl=fetch, onUsage})`：
  - `redirect:'error'`；非 2xx 抛错；
  - 校验返回：每个 `index` 是 `0..documents.length-1` 的整数且不重复，`relevance_score` 是有限数；不满足就抛错。允许返回条数少于输入（缺的视为未评分）。
  - 返回 `[{index, score}]`（按 score 降序）。
  - `onUsage` 只收元数据：`{at, model, documents:n, tokens, outcome, httpStatus, durationMs}`，不含查询文本、文档文本、密钥、返回体。

## R3 接入查询（`lib/memory-query.js` 的 `search()`）

插入点：向量复核循环（`if(vectors)while(true){…}`）结束之后、`const records=ordered().map(…)` 之前。

- `createMemoryQueryAnswer` 增加可选参数 `reranker`（默认 `null`）；`lib/index.js` 两处创建（约第 226、412 行）都传同一个 reranker 实例。
- 逻辑：
  1. `list=ordered()`；取前 `memoryRerankCandidates` 条且 `record.text.trim()` 非空的作为候选；候选少于 2 条则跳过（state `skipped`）。
  2. 时间预算：`budget=min(memoryRerankTimeoutMs, request.deadline - now() - packingReserveMs)`；`budget < 200` 则跳过（state `no_time`）。用 `AbortSignal.any([request.signal, AbortSignal.timeout(budget)])`。
  3. 每条文档文本 = `record.text` 截到前 1000 个字符（不切断代理对）；查询用 `request.query`。
  4. 成功：候选按 score 降序重排；未评分的候选按原顺序接在已评分候选之后；候选之外的记录保持原顺序接在最后。给重排后的每条记录设新 rank，保证 `compareRank` 排序结果就是重排顺序（例如 `rank = 1 + (候选数 - 位置)/候选数`，它们都大于任何 RRF 分数；非候选保持原 rank）。
  5. 失败 / 超时 / 返回格式错：保持原顺序，state 为 `failed` / `timeout`，记一行 `warn`（只写状态与 HTTP 码，不写文本）。
  6. 用户主动取消（`request.signal` 中止）照原逻辑抛出，不吞掉。
- 结果 `channels.rerank={state:'applied'|'skipped'|'no_time'|'failed'|'timeout'|'disabled'|'paused', candidates:n}`。重排状态**不**设 `degraded`（失败只是退回原顺序）。
- `validateResult` 里的回退记录（`_textFallback`）：当 `result.channels.rerank?.state==='applied'` 时，回退记录沿用被替换记录的 `_rank`，避免重排顺序被重新打乱；未重排时保持现有行为不变。
- 纠正优先（`newestCorrection` 把一条较新纠正放到第一位）的现有规则不变，仍在重排之后执行。

## R4 reranker 运行对象（新文件 `lib/memory-rerank.js`）

- `createMemoryReranker({config, fetchImpl, now, logger})` 返回 `{ enabled(), rerank({query, documents, signal}), status() }`。
- 首次使用时读 key 文件（trim）；读不到 → state `disabled`，原因“重排密钥不可用”。
- **熔断**：一次 HTTP 错误或格式错误后暂停 10 分钟（`paused`），期间直接跳过不发请求；超时不触发熔断（只是这一次没来得及）。
- `status()` 返回：`{enabled, model, service:主机名, state:'off'|'ready'|'paused'|'unavailable', reason, calls, failures, lastState, lastAt, tokens}`，都是本次进程内计数，不写文件、不含文本。

## R5 设置保存（`lib/deployment-config.js` + `lib/settings-host.js`）

- 新函数 `stageDeploymentRerank(file, input, expectedRevision)`：仿照 `stageDeploymentHandoff` 的加锁、版本冲突写法。
  - `input={enabled, serviceId, model, candidates, cloudConfirmed}`。
  - `enabled=true` 时：`serviceId` 必须是 `cfg.embeddingServices` 里有 key 的一条；`cloudConfirmed===true`，否则报“开启重排会把候选记忆片段发送到所选服务，请先确认”；把该服务的 `apiBase`、`apiKeyFile` 复制进 `cfg.memory.memoryRerankApiBase / memoryRerankApiKeyFile`，同时写 `memoryRerankServiceId`、`memoryRerankModel`、`memoryRerankCandidates`。
  - `enabled=false` 时：只把 `memoryRerank` 写成 false，其他字段保留（方便再次开启）。
  - 返回 `{rerank:公开字段（不含 key 文件路径）, revision}`。
  - 写入后**不**调用 afterSave；生效时机是重启 DSH（重新加载记忆框架）。
- `embeddingServiceInUse` 要把“被重排使用中”也算作使用中：被 `cfg.memory.memoryRerankServiceId` 引用、且 `memoryRerank===true` 的服务不能删除、不能改地址/密钥（报错文案：“这个服务正被重排使用；要删除请先关闭重排”）。
- `removeUnusedStagedKey` 等清理逻辑不得删掉重排正在引用的 key 文件。
- `readDeploymentSettings` 返回 `rerank` 公开字段（`enabled, serviceId, model, candidates`），不含 key 路径。
- 路由：`POST /rerank` → `stageDeploymentRerank(configurationFile, input, input?.revision)`。
